# AGENTS.md

## Главное правило

**`README.md` — для людей. Не редактируй `README.md` и не меняй его структуру без явной инструкции пользователя.** Если для выполнения задачи кажется нужным обновить README, сначала спроси и дождись прямого указания.

README описывает запуск, состав репозитория и команды. Технические детали, которые меняются от задачи к задаче, в него не добавляй.

## Куда что кладём

- `docs/` — только постоянная документация, которая остаётся верной при развитии проекта: схемы данных, правила, архитектурные договорённости. Статусы, планы, отчёты и исследовательские журналы сюда не кладём.
- `work/` — временные кэши, выгрузки, ответы API, исследовательские материалы и разовые скрипты. Каталог в `.gitignore`; в Git он не попадает.
- `archive/` — старые документы и история решений. Не используй архив как действующую документацию и не восстанавливай из него устаревшие правила без отдельного решения.
- `scripts/` — только повторяемые инструменты, которые входят в сборку, проверку или регулярный конвейер. Разовые загрузчики, ручные выборки и миграции создавай в `work/`. Если разовый инструмент стал регулярным, переноси его в `scripts/`, добавляй прогресс, тесты и документацию.

## Что за проект

- React + TypeScript + Vite + Leaflet; точка входа — `src/App.tsx`, карта — `src/MapView.tsx`.
- `vite.config.ts` задаёт `base: './'`, чтобы `dist/` работал в подкаталоге GitHub Pages.
- Исходные карточки — `data/atlas/<city>/<id>.json`, по одному JSON на объект. Справочники стилей, архитекторов, районов и подписей дат — `data/aux/<city>/*.json`; они склеиваются в генерируемый `data/aux/<city>.json`.
- Ориентиры — `data/landmarks/<city>/<id>.json`.
- Фотографии — `data/photos/<city>/<sha256>.webp` и sidecar `<sha256>.metadata.json`; превью — `data/thumbnails/<city>/`.
- `raw/osm/` — сохранённые выгрузки OSM, из которых `scripts/build-data.py` собирает слои карты.
- `public/atlas/` — генерируемый каталог: `buildings.json`, `landmarks.json`, `manifest.json`, `basemap.geojson`, `building-outlines.geojson`, `photos/`, `thumbnails/`. Не редактируй его вручную; всё это создают `npm run build`, `npm run check` и `npm run dev`.
- `dist/` — результат `npm run build`, статический сайт.

## Команды

```sh
npm ci
npm run dev
npm run check
npm test
npm run build
npm run verify
```

- `npm run check` собирает данные, превью и рейтинги, проверяет TypeScript и целостность данных.
- `npm run build` делает полную сборку в `dist/`.
- `npm run verify` проверяет `dist/` по манифесту; запускай после сборки.
- Для пересборки слоёв карты нужен Python 3; для превью и рейтинга фотографий — Pillow.

## Правила данных

- Не выдумывай годы, стили, архитекторов, истории, адреса и объекты на фотографиях. Неизвестное значение должно быть явно пустым или «не установлено».
- Каждый объект атласа обязан иметь реальный контур `Polygon`/`MultiPolygon`. Не заменяй отсутствующую геометрию точкой или придуманным прямоугольником.
- Координаты в JSON и GeoJSON — `[longitude, latitude]`; Leaflet получает `[latitude, longitude]`.
- Не добавляй растровые OSM-тайлы, bitmap-подложки, `L.tileLayer` или сплошную фоновую карту из внешнего сервиса. Карта работает на локальных векторных слоях; при необходимости расширяй конкретные категории GeoJSON.
- Фотографии адресуются по SHA-256 содержимого. Не переименовывай их вручную и не редактируй sidecar без необходимости; обязательные поля sidecar — `author`, `license`, `licenseUrl`, `source`, `modifications`, `width`, `height`, `rating`.
- `public/atlas/`, `data/aux/<city>.json`, `data/thumbnails/`, `dist/` и `.cache/` — генерируемые артефакты. Меняй источники в `data/`, `raw/` и `src/`, а не результат сборки.
- После изменения данных или сборщика запускай `npm run check`; для проверки итогового сайта — `npm run build` и `npm run verify`.

## Рабочие ограничения

- Не запускай `make` и `docker`; эти команды запускает пользователь.
- Не устанавливай браузеры и инструменты автоматизации (Chromium, Playwright, Puppeteer). Вёрстку проверяй по коду и сборке; визуальную проверку в браузере выполняет пользователь.
- Перед правкой смотри `git status` и не перезаписывай пользовательские изменения.
- Не используй широкие команды удаления. Удаляй только конкретные проверенные пути.
- Для проверки страницы используй HTTP(S), а не `file://`.
