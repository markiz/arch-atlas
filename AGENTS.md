# Контекст проекта для агента

## Что строим

Это статический веб-атлас архитектуры Тбилиси. Основной экран — карта с цветными контурами интересных исторических зданий по периоду постройки; при выборе здания открывается инспектор с описанием, датой, архитектором, стилем, несколькими фотографиями и источниками. Второй экран — каталог с поиском и фильтрами. Обычные жилые многоэтажки не добавлять только ради заполнения карты. Интерфейс на русском; тексты должны быть полезными, без декоративных слоганов.

Текущий исследовательский набор содержит только объекты с Polygon/MultiPolygon; актуальное число карточек и полноту полей смотрите в `data/atlas/tbilisi/*.json` и в собранном `public/atlas/buildings.json`, а не в README. Переключатель Батуми/Кутаиси пока показывает честное пустое состояние, наборов зданий для них нет.

## Архитектура и точки входа

- React + TypeScript + Vite + Leaflet; `index.html` обязателен в корне. `vite.config.ts` задаёт `base: './'`, чтобы `dist/` работал в подкаталоге GitHub Pages.
- `src/App.tsx` загружает `public/atlas/manifest.json` и только данные карты; фотографии не входят в начальную загрузку. Каталог лениво запрашивает превью видимых карточек, а при выборе объекта `src/photos.ts` сначала скачивает все превью, затем полные файлы галереи, проверяет SHA-256 и создаёт Blob URL. Здесь также каталог, поиск, фильтры, галерея и инспектор.
- `src/MapView.tsx` рисует локальные векторные слои из `public/atlas/basemap.geojson` и поверх них контуры зданий атласа. Для расширения карты используются только отобранные локальные слои улиц, парков/зелёных зон и музеев; полный городской слой обычных зданий по умолчанию не показывается. Обзор города — зум около 11.5; клик по зданию и «Показать на карте» открывают его на более крупном масштабе. Геолокация запускается только кнопкой.
- Не добавляйте растровые OSM-тайлы, bitmap-подложки, `L.tileLayer` или сплошную фоновую карту из внешнего сервиса. Они не нужны проекту и ухудшают читаемость. Не возвращайте их по упоминанию в истории или старой документации. Если нужно расширить покрытие, добавляйте только конкретные нужные векторные категории в GeoJSON, сохраняя сдержанный стиль и независимые переключатели слоёв.
- `src/domain.js` содержит периоды/цвета и фильтрацию; `src/types.ts` описывает записи. Не меняйте цвета или смысл датировки только в одном из слоёв интерфейса.
- `public/atlas/` — целиком генерируемый каталог, в Git не хранится: `buildings.json` собирает `scripts/assemble-atlas.mjs`, `basemap.geojson` и `building-outlines.geojson` — `scripts/build-data.py` (через `scripts/build-map-layers.mjs`, который пропускает шаг, пока не изменился хеш входов в `raw/`), `manifest.json` — `scripts/create-manifest.mjs`, `photos/` и `thumbnails/` — `scripts/sync-photos.mjs` из `data/photos/` и `data/thumbnails/`. `npm run build`, `npm run check` и `npm run dev` сами создают недостающее; превью генерирует `scripts/create-photo-thumbs.py`. На чистом клоне нужен Python 3 (он есть в Docker-образе). Подложка карты работает на локальных данных; во время просмотра внешние карты и тайловые серверы не запрашиваются. Сохраняйте подпись и атрибуцию OpenStreetMap для использованных векторных данных.

## Данные и редактура

- Google-ссылка каждой карточки должна вести на конкретное место, а не на голую координату. Для этого нужен проверенный `googlePlaceId`, точка которого находится не дальше 15 м от контура здания (цель — 10 м); если Google не различает объект или ближе 15 м метки нет, карточка обязана иметь полный адрес (минимум `addresses.en`), и ссылка строится поиском по названию и адресу. Координатная ссылка допустима только при отсутствии и Place ID, и адреса. Place ID подбирайте по адресу (Geocoding forward) с проверкой номера дома, улицы и расстояния, затем проверяйте через Places API (New) Place Details; для именованных достопримечательностей используйте текстовый поиск. Не привязывайте ID соседнего дома или другого корпуса. Порядок и отчёт — [docs/google-place-id-manual-review.md](docs/google-place-id-manual-review.md).
- Публичные и правительственные здания не отсеиваются на этапе отбора. Все контуры с `building=public`, `building=government`, `building=civic`, `office=government` или `government=*` обязаны попасть в пул кандидатов на разбор, даже если у них нет `heritage`/`historic`. Это правило про кандидатов, а не про публикацию: типовая районная управа или налоговая может получить HOLD/REJECT с причиной, но не может быть отброшена только из-за отсутствия охранного тега. Значимость, дата, автор, фотографии и источники проверяются по обычному процессу; пул ведётся по правилам [docs/location-data-collection.md](docs/location-data-collection.md).
- Перед сбором данных для новой локации, обновлением источников, адресов/Place ID, геометрии или фотографий прочитайте [руководство по сбору данных](docs/location-data-collection.md). Оно описывает источники, детализацию, владельцев полей, ограничения сборщиков и порядок проверки; поддерживайте его актуальным при изменении процесса. Батч адресов: `scripts/batch-google-addresses.py`, источник — Google Geocoding API + Places API (New), допуск 5 м, результаты сначала в отдельный отчёт.
- Исходники карточек — `data/atlas/tbilisi/<id>.json`, по одному pretty-JSON на объект. Внутри лежат имена, адреса, содержательные описания (если они есть) и история со всеми переводами, координаты, контур, упорядоченный список sha256-идентификаторов фотографий и источники. Стиль, архитекторы, район и подпись датировки остаются ссылками (`styleIds`, `architectIds`, `districtId`, `yearLabelId`) в городские справочники `data/aux/tbilisi/{styles,architects,districts,year-labels}.json`; не дублируйте их подписи в карточке. `scripts/merge-aux.mjs` склеивает справочники в `data/aux/tbilisi.json` (генерируемый build-артефакт), а `scripts/assemble-atlas.mjs` — в `public/atlas/buildings.json`; `npm run build`, `npm run check` и Vite dev-сервер вызывают это автоматически. При `npm run dev` правка `data/atlas/**/*.json` или `data/aux/<city>/**/*.json` пересобирает JSON и перезагружает страницу.
- `scripts/build-data.py` собирает только `basemap.geojson` и `building-outlines.geojson` из сохранённых `raw/osm/grid/osm-grid-*.xml`, выборки нужных городских слоёв `raw/osm/osm-tbilisi-selected.json` и файлов в `data/`; карточки он не создаёт и не меняет. Устройство `raw/` и происхождение каждого файла — `raw/README.md`; не складывайте туда одноразовые пробы и ответы API по отдельным зданиям. В городскую подложку не добавляйте массовую выгрузку всех объектов OSM: включайте только согласованные тематические категории (улицы, парки/зелёные зоны, музеи и другие конкретно запрошенные слои), не добавляйте обычные здания и посторонние POI ради полноты. После правки исходных данных запускайте генератор, если он владеет затронутым полем, затем собирайте манифест командой `npm run build`.
- Координаты в JSON и GeoJSON идут как `[longitude, latitude]`; Leaflet получает `[latitude, longitude]`. Каждый объект атласа должен иметь реальный контур Polygon/MultiPolygon: не подменяйте отсутствующую геометрию точкой или придуманным прямоугольником.
- `minYear`/`maxYear` могут быть `null`. Не выдумывайте год, стиль, архитектора, историю или конкретное здание на фотографии. Для неизвестных сведений сохраняйте явное «не установлено». Указывайте проверяемые источники и отмечайте неуверенность.
- Фотографии лежат локально в WebP и адресуются по SHA-256 содержимого: полный файл — `data/photos/<city>/<sha256>.webp`, его метаданные — `data/photos/<city>/<sha256>.metadata.json`, превью — `data/thumbnails/<city>/<sha256>.webp` (ширина до 720 px, пропорции сохраняются, без апскейла). В исходной карточке `photos` — только упорядоченный массив sha256; `file` и `thumb` (`photos/<city>/<sha256>.webp`, `thumbnails/<city>/<sha256>.webp`) и поля метаданных подставляет `scripts/assemble-atlas.mjs` из sidecar-файлов. Отдельного `photos.json` нет: канонический словарь — это sidecars, поэтому нет второго источника истины. `data/thumbnails/` генерируется и в Git не хранится; превью создаёт `scripts/create-photo-thumbs.py`, а `npm run build`, `npm run check` и `npm run dev` вызывают генерацию сами. Публикуемые зеркала `public/atlas/photos/` и `public/atlas/thumbnails/` генерируются, не редактируйте их вручную. Sidecar обязан содержать `author`, `license`, `licenseUrl`, `source`, `modifications`, `width` и `height` — фактические пиксельные размеры сохранённого WebP, — а также `rating` (детерминированная оценка 0–100). Необязательные поля: `description`, `sourceTags` (сырые теги/категории источника, для Commons — категории файла) и `visualTags` (стандартизованные оптические теги из `data/photo-visual-tags.json`, 43 тега, включая quality; их назначает модель по контактным листам по 6 фото, автоматического классификатора нет; служебный `scripts/photo-visual-review.py` только готовит листы и записывает готовые теги). Размеры синхронизирует `scripts/sync-photo-dimensions.py` (`npm run photos:dimensions`), рейтинг считает `scripts/rate-photos.py` (`npm run photos:rate`); они попадают в `buildings.json` и проверяются сборкой. В основном режиме рейтинг задаёт порядок галереи и скрывает снимки <50, если у объекта есть три снимка >50. Имя файла — это хэш его байтов: изменение изображения автоматически даёт новый id, а одинаковые снимки разных объектов делят один файл и один sidecar. Целевой минимум — три разных снимка на объект, когда есть проверяемые кандидаты; дубли одного кадра, интерьеры, таблички и кадры с несколькими объектами не добивают галерею. Ширина: до 1920 px для свободных лицензий, до 1200 px для неизвестных и коммерческих источников, без апскейла. Для Commons не тяните оригинал напрямую: Wikimedia отдаёт только стандартные миниатюры (960/1280/1920 px), а произвольные ширины и оригиналы отклоняет; маленькие снимки восстанавливает `scripts/upgrade-photo-sources.py` (`npm run photos:upgrade`). Для реестра памятников не ограничивайтесь `PhotoAddress`: `scripts/fetch-registry-photos.py --review` запрашивает `api/Immovable/GetImmovableObject` и собирает все `photoIds`, а `--apply` берёт ручной отбор из `data/registry-photo-selection.json`. В записи часто есть тот же кадр в большем размере и несколько ракурсов; маленький дубль заменяйте самой крупной версией, берите три-четыре разных общих вида, а кадры деталей, ограды и соседних зданий не добивают галерею. Для пакетной обработки используйте `scripts/batch-registry-review.py` (один лист на карточку), `scripts/plan-registry-review.mjs` и `scripts/merge-registry-selections.mjs`; применение — `fetch-registry-photos.py --apply --selection-dir work/registry-batch/selections --allow-fewer`. Проверяйте, что снимок изображает именно нужное здание (в том числе по категориям файла), и сохраняйте атрибуцию; права на фотографию и права на изображённое произведение архитектуры требуют отдельной проверки. Приоритет — свободным лицензиям; если их нет, допустимо фото реестра в низком разрешении с явной пометкой «лицензия не установлена» и ссылкой на источник. Фото Google Maps/Places не переносить. Основной конвейер — `scripts/collect-photo-candidates.py` и `scripts/apply-photo-candidates.py`. Полная политика — [docs/photo-policy.md](docs/photo-policy.md). Часть карточек собрана автоматически из OSM/Wikidata/Commons и пока не прошла ручную редактуру.
- Ссылки и атрибуцию OpenStreetMap сохраняйте. Карта не должна становиться пустой вне районов с объектами атласа.

## Скрипты и прогресс

Одноразовые исследовательские скрипты — разовые загрузчики, ручные выборки, миграции под конкретную задачу — не добавляйте в `scripts/`. Создавайте их в `work/` (каталог в `.gitignore`). В `scripts/` остаются только повторяемые инструменты сборки, проверки и конвейера. Если разовый скрипт стал частью регулярного процесса, перенесите его в `scripts/`, добавьте прогресс, документацию и тесты.

Любой новый или изменяемый скрипт, который тянет данные из сети, разбирает большие выгрузки, собирает или проверяет сотни объектов либо может работать дольше нескольких секунд, обязан показывать прогресс по ходу работы. Это относится и к `fetch-*.py`, и к `build-*.py`, `queue_*.py`, `validate_cards.py`, `create-*.mjs`.

Минимум: стартовая строка с планом, счётчик `выполнено/всего`, процент, прошедшее время, ETA по фактической скорости и метка текущего элемента; финальная строка и сводка `ok/skipped/error`. ETA нельзя выдумывать: при неизвестном общем числе показывайте счётчик и скорость без ETA. Прогресс пишется в stderr, итоговые данные — в stdout; потоки и промисы обновляют счётчик после завершения элемента. Многофазные скрипты показывают отдельный прогресс на фазу. Секреты и URL с ключами в прогресс не попадают.

Готовые helper'ы: `scripts/progress.py` (`Progress`) и `scripts/lib/progress.mjs` (`Progress`). Полные правила, примеры и чек-лист — [docs/long-running-scripts.md](docs/long-running-scripts.md). Не оставляйте новый загрузчик или сборщик, который молча висит на сотне запросов.

## Работа и публикация

Codex никогда не запускает команды `make` и `docker`. Их запускает пользователь самостоятельно.

Из корня проекта: `npm ci`, `npm run dev` для разработки; `npm run check`, `npm test`, `npm run build`, `npm run verify` по необходимости. `npm run build` создаёт `dist/`; `dist/` — готовый статический сайт, исходники держите отдельно. Для проверки страницы используйте HTTP на `localhost` или HTTPS, не `file://`.

Не устанавливайте браузеры и инструменты автоматизации (Chromium, Playwright, Puppeteer) и не скачивайте их ради проверки страницы: браузера в окружении нет, и ставить его не нужно. Вёрстку и поведение интерфейса проверяйте по коду и сборке; визуальную проверку в браузере при необходимости выполняет пользователь.

`make image` собирает Docker-образ с Node, зависимостями и Codex CLI. `make codex` запускает CLI с `--no-daemon --dangerously-bypass-approvals-and-sandbox`, монтирует репозиторий и сохраняет вход/сессии в именованном Docker-томе `atlas-codex-home`; для первого входа — `make codex ARGS="login --device-auth"`. Контейнер запускается от UID/GID пользователя, с read-only корневой файловой системой, временным `/tmp`, без Linux capabilities и без повышения привилегий; записываемыми остаются примонтированные `/workspace` и `/codex`. Не добавляйте `--privileged` и не расширяйте права контейнера для обхода ограничений Codex. В образе есть `procps` (`ps`) и `bubblewrap`. При изменении Dockerfile или lockfile пересобирайте образ.

`make build` **не равен** обычному `npm run build`: он создаёт локальный коммит сайта в ветке `gh-pages` через Docker, не переключая текущую ветку. `make push` отправляет эту ветку с хоста. Пользователь предпочитает делать push самостоятельно; не запускайте `make push` без его прямого запроса. Прямой запуск `bash deploy-pages.sh` по умолчанию **делает push** — используйте его только осознанно; `PAGES_PUSH=no` оставляет коммит локально. Если ветка Pages уже есть на remote, сначала синхронизируйте её на хосте. Скрипт публикации собирает дерево ветки заново из текущей сборки: устаревшие ассеты (старые бандлы, удалённые фотографии) из ветки удаляются, из прошлого дерева переносится только `CNAME`. Не возвращайте публикацию «поверх» старого дерева: ветка начнёт копить мёртвые файлы.

Перед правкой смотрите состояние Git и не перезаписывайте пользовательские изменения. Не используйте широкие команды удаления для очистки проекта или временных папок. Изменения данных, интерфейса и публикации делайте отдельными понятными правками. Для крупного изменения проверьте сборку; работу в браузере проверяет пользователь, а компиляция сама по себе не подтверждает работу карты, сети, геолокации и мобильной панели.

`README.md` описывает запуск и ограничения текущей версии. `docs/status.md` — текущий снимок состояния, `docs/README.md` — указатель действующих документов. `docs/archive/` — исторические документы, разложенные по папкам: `planning/`, `status/`, `reviews/` и `research/` (исследовательские журналы по очередям 1–4). При расхождении сверяйтесь с кодом и обновляйте документацию.
