# Архитектурный атлас Тбилиси

Клиентское статическое приложение на React, TypeScript, Vite и Leaflet. Исторические здания Тбилиси на карте, фотографии, каталог, поиск, фильтры, локальная подложка и определение местоположения по запросу пользователя.

Каталог расширен автоматизированным отбором объектов, отмеченных как исторические или охраняемые в OpenStreetMap, с дополнением данных Wikidata. Новые карточки, архитектурные атрибуции, фотографии и права требуют редакционной проверки. Неизвестные данные не заполняются предположениями: отсутствие фотографии или датировки обозначено в карточке явно.

## Готовый сайт

Каталог `dist` можно положить на любой статический HTTPS-хостинг. Для локальной проверки:

```sh
python3 -m http.server 8000 --directory dist
```

Откройте `http://localhost:8000/`. Для GitHub Pages копируйте содержимое `dist` в корень выбранной публикационной ветки. Атлас также работает в подкаталоге, например `https://username.github.io/repository/`.

`file://` не поддерживается. Для геопозиции и проверки SHA-256 нужен HTTPS или `localhost`. Данные атласа и векторная подложка загружаются из локального пакета. Фотографии не входят в начальную загрузку: каталог лениво подгружает превью видимых карточек, а после клика по объекту сначала загружаются все его превью, затем полные файлы галереи. Внешние карты и тайловые серверы при просмотре не запрашиваются. Запуск закрытой страницы без сети (PWA) не реализован.

## Исходники

Нужны Node.js и npm:

```sh
npm ci
npm run check
npm test
npm run build
npm run verify
npm run dev
npm run layers:build
npm run aux:merge
npm run photos:thumbs
```

Для live-разработки в Docker выполни `make dev` и открой `http://localhost:5173/`. Сервер пересобирает изменённые модули и обновляет страницу без перезапуска; правка JSON в `data/atlas/` также пересобирает `public/atlas/buildings.json` и перезагружает страницу. Проверка изменений работает через опрос файловой системы, в том числе при Docker bind-mount. Чтобы выбрать другой локальный порт, укажи, например, `make dev DEV_PORT=4173`.

Переменные окружения для контейнера можно положить в `.env` (образ их не содержит). Файл игнорируется Git и Docker build context. Для собственного файла укажи `ENV_FILE`, например `make codex ENV_FILE=.env.local`; тот же параметр поддержан командами `make dev` и `make build`. Если `.env` не существует, команды запускаются без `--env-file`. `.env.example` содержит шаблон; скопируй его в `.env` и заполни нужные значения.

- `src/` — интерфейс, Leaflet-карта и геопозиция, галерея, локальные поиск и фильтры.
- `data/atlas/tbilisi/<id>.json` — исходные карточки: по одному pretty-JSON на объект, с переводами, контуром и фотографиями. `styleIds`, `architectIds`, `districtId` и `yearLabelId` остаются ссылками в городские справочники, а не дублируются в карточке.
- `data/aux/tbilisi/styles.json`, `architects.json`, `districts.json`, `year-labels.json` — редактируемые справочники города: ID, исходная подпись и переводы на четыре языка. `scripts/merge-aux.mjs` склеивает их в `data/aux/tbilisi.json` — единый JSON города для сборки; он генерируется и не публикуется.
- `data/photos/<city>/<sha256>.webp` — полные фотографии; ширина до 1920 px для свободных лицензий и до 1200 px для неизвестных/коммерческих источников, без апскейла. Рядом лежит `<sha256>.metadata.json` с автором, лицензией, источником, изменениями, фактическими `width`/`height` сохранённого WebP, необязательным описанием, сырыми `sourceTags` источника и стандартизованными `visualTags`. Имя файла — SHA-256 его байтов, поэтому изменение изображения автоматически даёт новый id, а одинаковые снимки разных объектов делят один файл. В исходной карточке `photos` — только упорядоченный массив sha256; `file`, `thumb` и метаданные подставляет `scripts/assemble-atlas.mjs`. `data/thumbnails/<city>/<sha256>.webp` — сгенерированные превью шириной до 720 px, с сохранением пропорций и без апскейла. `data/thumbnails/` в Git не хранится; `public/atlas/photos/` и `public/atlas/thumbnails/` — сгенерированные зеркала для публикации, их создаёт `scripts/sync-photos.mjs`; вручную их не редактируют.
- `public/atlas/` — целиком генерируемый каталог, в Git не хранится. `buildings.json` собирает `scripts/assemble-atlas.mjs`, `basemap.geojson` и `building-outlines.geojson` — `scripts/build-data.py` через `scripts/build-map-layers.mjs`, `manifest.json` — `scripts/create-manifest.mjs`, `photos/` и `thumbnails/` — `scripts/sync-photos.mjs`, превью — `scripts/create-photo-thumbs.py`. Готовый `buildings.json` — общий JSON Тбилиси для приложения; контуры обычных зданий загружаются только при включении слоя «Силуэты зданий». Всё это создают `npm run build`, `npm run check` и `npm run dev`, поэтому на чистом клоне ничего докладывать вручную не нужно.
- `raw/osm/osm-tbilisi-selected.json` — улицы, парки и музеи; `raw/osm/osm-tbilisi-building-outlines.geojson` — около 121 тыс. контуров зданий по административной границе Тбилиси из локально обработанного регионального PBF. Устройство каталога и происхождение каждого файла — [raw/README.md](raw/README.md).
- `scripts/extract-tbilisi-building-outlines.py` извлекает городской слой из PBF Geofabrik (нужны PyOsmium и Shapely); `scripts/build-data.py` собирает только подложку и контуры зданий; `scripts/build-map-layers.mjs` вызывает его из сборки и пропускает, если хеш входов не менялся; `scripts/assemble-atlas.mjs` упаковывает карточки и подмешивает sidecar-метаданные фотографий; `scripts/create-manifest.mjs` считает размеры и SHA-256; `scripts/sync-photos.mjs` публикует фотографии и превью из `data/photos/` и `data/thumbnails/`; `scripts/create-photo-thumbs.py` создаёт недостающие превью шириной до 720 px; `scripts/sync-photo-dimensions.py` записывает в sidecar реальные ширину и высоту WebP; `scripts/sync-photo-source-tags.py` переносит в sidecar категории/теги источника; `scripts/upgrade-photo-sources.py` возвращает маленьким снимкам больший допустимый размер из источника; `scripts/photo-visual-review.py` готовит контактные листы по 6 фото и записывает уже проверенные моделью `visualTags` (сам не классифицирует); `scripts/merge-aux.mjs` собирает городские справочники в единый aux JSON.
- `scripts/queue_collect.py`, `scripts/queue_report.py` и `scripts/validate_cards.py` — сбор фактов по очереди, отчёт и проверка исходных карточек и собранного JSON; `queue_*` работают с `work/`.
- `scripts/collect-photo-candidates.py` и `scripts/apply-photo-candidates.py` — основной конвейер галерей: поиск свободных снимков Commons по Wikidata (P18/P180), тегу OSM, улице с номером дома, названию и координатам, проверка по категориям и почти-дублям, затем скачивание и запись в карточки с шириной 1920/1200 px и целью в три фотографии. Кандидаты и отчёты складываются в `work/photo-research/`; в карточки пишет только второй скрипт. После него превью создаёт `npm run photos:thumbs` (или обычная сборка). Для реестра памятников `scripts/fetch-registry-photos.py --review` собирает все `photoIds` записи и контактные листы, а `--apply` берёт ручной отбор из `data/registry-photo-selection.json`, заменяет маленькие дубли крупными версиями и добивает галерею до трёх-четырёх видов. Пакетная подготовка — `scripts/batch-registry-review.py` (один лист на карточку, `work/registry-batch/`), нарезка на батчи — `scripts/plan-registry-review.mjs`, слияние отборов — `scripts/merge-registry-selections.mjs`; применение к пачке — `fetch-registry-photos.py --apply --selection-dir work/registry-batch/selections --allow-fewer`.
- `scripts/fetch-selected-photos.py` и `scripts/fetch-fallback-photos.py` — точечные загрузчики свободных фото Commons и одиночного фото реестра с пустыми автором и лицензией; они сохраняют файл в `data/photos/tbilisi/<sha256>.webp`, sidecar рядом и добавляют id в упорядоченный `photos` карточки, после чего превью создаёт `npm run photos:thumbs` либо `npm run build`. Если у записи реестра несколько файлов, используйте `scripts/fetch-registry-photos.py`. Правила — [docs/photo-policy.md](docs/photo-policy.md).
- `scripts/resolve-geometries.py` обновляет контур в файле объекта и требует Python-пакет Shapely.
- `data/photo-candidates.json` и `data/photo-fallbacks.json` — исследовательские кандидаты, а не исходники карточек. `data/photo-gallery-selection.json` — ручной отбор источников Commons после визуальной проверки; из него добавляет фото `scripts/apply-photo-candidates.py`. `data/registry-photo-selection.json` — ручной отбор `photoIds` реестра для `scripts/fetch-registry-photos.py --apply`. Кэш и отчёты конвейера лежат в `work/photo-research/` (каталог не публикуется).
- Длительные загрузчики, сборщики и проверки печатают прогресс в stderr: сколько выполнено, процент, прошедшее время, ETA и скорость; итоговые данные остаются в stdout. Правила и общие helper'ы — [docs/long-running-scripts.md](docs/long-running-scripts.md).

Чтобы пересоздать данные из приложенных OSM-выгрузок и локальных редакционных файлов, выполните `python3 scripts/build-data.py` (подложка и контуры), затем `npm run build` (упаковка карточек, манифест и `dist/`). `npm run build` и `npm run check` вызывают `scripts/build-map-layers.mjs`: он хеширует `raw/`, редакционные переводы и сам `build-data.py`, пересобирает слои только при изменении входа (около 5 с) и иначе пропускает шаг (около 0,2 с). Отметка лежит в `.cache/map-layers.json` и не коммитится; `npm run layers:force` пересобирает принудительно. Для самого шага нужен Python 3 — если его нет, а готовые `public/atlas/*.geojson` уже лежат, сборка использует их с предупреждением. При `npm run dev` изменение `data/atlas/**/*.json`, `data/photos/**`, `raw/**` или редакционных переводов автоматически пересобирает общий JSON, создаёт недостающие превью, публикует фотографии и перезагружает страницу. Скрипты загрузки предоставлены для исследования и требуют сети; повторная выгрузка внешних источников может изменить исходные данные.

Источники, детализация, порядок добавления города и батч адресов/Place ID через Google API описаны в [руководстве по сбору данных](docs/location-data-collection.md). Указатель действующих документов — [docs/README.md](docs/README.md); исторические документы и ранние снимки — в [архиве](docs/archive/README.md).

## Публикация в GitHub Pages

Из корня репозитория с исходниками:

```sh
bash deploy-pages.sh
```

По умолчанию скрипт собирает текущую рабочую версию и отправляет только содержимое `dist` в ветку `origin/gh-pages`. Дерево ветки каждый раз собирается заново из текущей сборки, поэтому устаревшие файлы (старые бандлы, удалённые фотографии) из ветки исчезают; из прошлого дерева переносится только `CNAME`. Историю ветки скрипт сохраняет. Исходную ветку и индекс не переключает. Временную папку не удаляет и показывает её путь. Для другого remote или ветки:

```sh
PAGES_REMOTE=origin PAGES_BRANCH=gh-pages bash deploy-pages.sh
```

В GitHub необходимо один раз открыть Settings → Pages и выбрать Deploy from a branch → `gh-pages` / `(root)`. Скрипт использует текущие файлы, даже если они ещё не закоммичены.

## Публикация через Docker

Из корня полного Git-репозитория с исходниками (включая `index.html`, `src/`, `package.json` и `package-lock.json`, а также Docker-файлы):

```sh
make image
make build
```

`make build` соберёт сайт и запишет результат локальным коммитом в `gh-pages` внутри подключённого репозитория. Контейнер не делает push и не требует SSH-ключей или сетевого доступа к Git remote. Подключённая папка доступна на запись, поскольку контейнер обновляет Git-ветку. Имя и email автора коммита берутся из Git-конфигурации на хосте. Чтобы отправить ветку:

```sh
make push
```

Remote и ветку можно переопределить: `make build REMOTE=upstream BRANCH=site-pages`, затем `make push REMOTE=upstream BRANCH=site-pages`.

### Codex CLI в Docker

Образ также содержит Codex CLI и `bubblewrap` для Linux-песочницы. Запусти CLI из корня проекта:

```sh
make image
make codex
```

Команда запускает интерактивный `codex --no-daemon --dangerously-bypass-approvals-and-sandbox` в `/workspace`: Codex не запрашивает подтверждения и не применяет свою внутреннюю песочницу. Изоляцию обеспечивает Docker: процесс работает с UID/GID пользователя, без Linux capabilities и повышения привилегий; корневая файловая система контейнера доступна только для чтения, `/tmp` — временный `tmpfs`. Запись разрешена в смонтированный `/workspace` и отдельный том `/codex`. Настройки и вход хранятся в томе `atlas-codex-home`, а не на хосте и не в образе. Первый вход выполни так:

```sh
make codex ARGS="login --device-auth"
```

После авторизации запускай `make codex`; данные останутся в томе между контейнерными сессиями. Чтобы выбрать другое имя тома: `make codex CODEX_VOLUME=my-codex-home`. Для других аргументов, например версии CLI: `make codex ARGS="--version"`. Режим Codex с максимальными правами действует внутри доступов контейнера: он может свободно менять файлы в `/workspace` и `/codex`, а также обращаться к сети. Docker при этом не запускается в `--privileged` режиме.

### DeepSeek Harness

Запусти веб-интерфейс DeepSeek Harness из контейнера командой:

```sh
make deepseek
```

Команда собирает отдельный образ из `Dockerfile.deepseek` и запускает `dsh web`. Открой URL с токеном, который Harness выведет в терминале; адрес сервера доступен только на хосте по `127.0.0.1:3080`. Останови его через `Ctrl+C`. Чтобы выбрать другой порт, укажи `make deepseek DEEPSEEK_PORT=3081`.

Каталог проекта подключается в контейнер как `/workspace`, как и в остальных командах Make. Настройки, сессии, нативный кэш и другие данные Harness хранятся отдельно от Codex в томе `atlas-deepseek-home`, в подкаталоге `/dsh/home`; при необходимости имя тома можно изменить через `DEEPSEEK_VOLUME`. В `.env` можно передать `DEEPSEEK_API_KEY`, либо настроить ключ в разделе Settings → Models веб-интерфейса.

В образе уже есть инструменты для работы с данными: `python3` с Pillow, Shapely и Pyosmium, `curl`, `wget`, ImageMagick (`convert`, `identify`) и `cwebp`. Кэш npm направлен в `/tmp/npm-cache`, потому что домашний каталог Harness недоступен для записи. Если на хосте не задан `git config user.name`, коммиты внутри контейнера подписываются как `Atlas Agent <atlas-agent@localhost>`; переопределить можно через `make deepseek GIT_NAME="Имя" GIT_EMAIL="адрес"`.

Если ветка `gh-pages` уже существует на remote, сначала получи её на хосте, чтобы новый коммит продолжил её историю:

```sh
git fetch origin gh-pages:refs/heads/gh-pages
```

Затем отправь ветку с хоста обычной командой:

```sh
git push origin gh-pages
```

Если имя ветки или remote отличаются, укажи `-e PAGES_BRANCH=site-pages` и при необходимости `-e PAGES_REMOTE=upstream`; последний влияет на подсказку команды push, но не вызывает соединение с remote. После изменения `package-lock.json`, `Dockerfile` или `deploy-pages.sh` повторно выполни `docker build`. Контейнер оставляет временную копию проекта внутри себя для осмотра и не удаляет её автоматически. `docker run` без `--rm` сохраняет остановленный контейнер; посмотреть его можно через `docker ps -a`.

## Ограничения

- Данные и фотографии некоторых объектов неполны; отсутствующие фотографии обозначены явно.
- В переключателе доступны Тбилиси, Батуми и Кутаиси; данные зданий пока есть только для Тбилиси. Векторные улицы, парковые зоны и музеи покрывают административную территорию Тбилиси; силуэты обычных зданий сохранены только в центральной подложке и по умолчанию скрыты.
- Полная браузерная E2E-проверка (визуальная, мобильная, геолокация, автономная работа) не выполнялась; для проверки используйте localhost или HTTPS.
- Для полноценного редакционного выпуска нужны проверка контуров, дат, авторства и фотографий, повышение полноты галерей и реализация расширенной схемы фаз из [исходного плана](docs/archive/planning/implementation-plan.md).
