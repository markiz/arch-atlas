# Интерактивный архитектурный атлас Тбилиси

План реализации и задания для передачи моделям-исполнителям. Версия 1.0, 31 октября 2026 года.

## 1. Что именно строим

Статический веб-сайт с двумя представлениями одного каталога:

1. **Карта — основной экран.** Отобранные здания показаны своими контурами и окрашены по времени постройки. Щелчок или касание открывает инспектор с фотографиями и сведениями.
2. **Каталог — дополнительный экран.** Список с поиском, фильтрами по времени постройки, архитектору и стилю. Из карточки можно перейти к зданию на карте.

Атлас редакционный, а не кадастровый: он показывает исторические и архитектурно значимые объекты, а не весь жилой фонд. Архитектурно выдающаяся многоэтажка может попасть в атлас; обычная типовая застройка — нет.

**Главный принцип:** надежные данные и понятная карта важнее количества карточек и эффектов.

## 2. Принятые решения и границы MVP

Это рабочие решения для первой реализации. Исполнители не должны самостоятельно заменять их другим продуктом или стеком.

| Вопрос | Решение |
|---|---|
| Размер первого релиза | 50 проверенных объектов; технический прототип сначала на 10 |
| Территория | Исторический центр и выбранные особенные объекты в пределах Тбилиси; точные границы покрытия фиксируются в задаче T01 |
| Язык интерфейса | Русский; грузинские названия, английские названия и исторические варианты используются в данных и поиске |
| Основная геометрия | Реальные Polygon/MultiPolygon; подтвержденная точка допустима как явно обозначенный запасной вариант |
| Карта | Плоская 2D-карта без 3D, спутниковых снимков и Street View |
| Данные | Версионируемые файлы в репозитории; обновление через новую сборку |
| Работа пользователя | Чтение, поиск, фильтрация, просмотр фото; без аккаунтов и редактирования |
| Развертывание | Готовая директория dist на обычном статическом HTTPS-хостинге |
| После загрузки | Все основные действия работают без новых сетевых обращений |
| Перезагрузка без сети | Отдельное последующее расширение; в MVP гарантируется работа уже открытой вкладки |

### Что означает «статически загрузить и больше не лезть на сервер»

Принимаем буквальную трактовку: после статуса «Атлас загружен» панорамирование, масштабирование, поиск, открытие любой карточки и любой включенной фотографии **не вызывают HTTP-запросов**. Статический хостинг нужен только для начальной доставки файлов.

Это сильнее обычного «нет бэкенда»: статический сайт с онлайн-тайлами или фотографиями, загружаемыми при открытии карточки, этому условию не соответствует.

Первая загрузка включает весь конечный пакет. Во время нее отображаются ход загрузки и фактический объем. Можно показать оболочку раньше, но готовность объявляется только после загрузки всех обязательных ресурсов. Если часть не загрузилась, показать ошибку и повтор; не выдавать неполный пакет за готовый.

В MVP не обещаем открытие index.html через file://. Проверяем работу по HTTP/HTTPS, включая запуск из подкаталога. Статический файловый сервер при разработке не является прикладным бэкендом.

Внешние ссылки на источники и лицензии могут открываться по явному действию пользователя; это выход из приложения и не часть автономного просмотра. Автоматические проверки сети не должны открывать такие ссылки.

### Не включать в MVP

Маршруты прогулок, навигацию, геолокацию, регистрацию, рейтинги, отзывы, пользовательские фотографии, CMS, серверный поиск, автоматический подбор «всех старых домов», многоязычный интерфейс, исторический слайдер с реконструкцией города, 3D и массовую генерацию текстов без проверки. Полноценный PWA с запуском после закрытия браузера — позже.

## 3. Как отбираем здания

Включать объект, если есть хотя бы одно подтвержденное основание:

- охранный статус или документированная историческая ценность;
- заметный образец архитектурного стиля, строительной техники или городской традиции;
- значимая работа конкретного архитектора;
- признанное особенное сооружение XX–XXI века;
- важный для истории города дом с содержательными подтвержденными сведениями.

Возраст сам по себе недостаточен. Для каждого включенного объекта обязательны `inclusionReason` и источники, на которых основан отбор. «Красивый фасад» без объяснения не основание.

Первый набор должен охватывать несколько периодов и типов: жилые исторические дома, общественные здания, религиозную архитектуру, модернизм, несколько современных исключений. Не устанавливать искусственных квот, заставляющих включать неподтвержденные объекты.

Минимум для публикации: проверенная идентичность здания, положение, название или адрес, причина включения, краткое описание с источником, минимум одна фотография с понятными правами. Цель — две характерные фотографии: общий вид и деталь. Неизвестные дата, стиль или архитектор допустимы с честной пометкой.

Утраченные здания и гипотетические реконструкции пока исключаем. Руины допустимы, если это существующий и узнаваемый объект. Доступность интерьера не предполагается и не обещается.

## 4. Поведение интерфейса

### 4.1. Карта

- Карта занимает основной экран. На ней тихая подложка: река, улицы, парки, немного ориентиров и подписей.
- Только объекты атласа имеют яркую окраску и открывают инспектор. Прочая застройка, если включена в подложку, нейтральная и неинтерактивная.
- Постоянно доступны переключатель «Карта / Каталог», поиск, фильтры, легенда, масштабирование и возврат к области атласа.
- На малом масштабе здания представлены цветными точками с увеличенной областью касания; на крупном — контурами. В каждый момент активен один способ представления, без двойных кликов и дублирования.
- Если точки перекрываются, щелчок показывает список попавших объектов. На крупном масштабе пересекающиеся контуры также не должны делать объект недоступным.
- Наведение мыши дает краткую подпись; все действия доступны без hover.
- Выбранное здание имеет отдельную контрастную обводку. Цвет периода сохраняется.
- Карта ограничена объявленным покрытием и поддерживаемыми масштабами. За границами не должно быть впечатления «весь город изучен, но зданий нет».
- Фильтры скрывают не подходящие объекты. Показывается «Найдено N из M». Географическое положение карты само по себе не фильтрует каталог.
- Изменение фильтров не должно постоянно перецентрировать карту. Предусмотреть явную кнопку «Показать найденные».

### 4.2. Инспектор

На широком экране — боковая панель справа, которая оставляет карту доступной. На узком — раскрываемая нижняя панель или отдельный полноэкранный слой с явной кнопкой закрытия.

Порядок содержимого:

1. Название, альтернативное/грузинское название, адрес.
2. Основная фотография; переключение фотографий, подписи, автор и лицензия.
3. Дата или интервал, архитектор/архитекторы с ролью, стиль/стили.
4. Короткое объяснение, чем здание интересно.
5. История основных перестроек и прежнее назначение, если сведения есть.
6. Источники и дата редакционной проверки.

Не выводить пустые поля и тире без объяснения. Использовать «Архитектор не установлен», «Точная дата неизвестна», «Стиль не классифицирован». Спорное авторство помечать как атрибуцию, а не установленный факт.

При открытии объекта вне текущего кадра подвести карту к нему с учетом занятой панелью площади. Закрытие сохраняет положение карты. Escape закрывает панель; после закрытия фокус возвращается к элементу, который ее открыл.

### 4.3. Каталог и фильтры

- Поиск по названию, адресу, прежним названиям, алиасам архитектора и названиям стиля.
- Поиск локальный. Для 50–150 объектов достаточно нормализации строк и поиска подстрок по токенам; отдельный поисковый сервис не нужен.
- Нормализация: Unicode NFC, нижний регистр, единый пробел, унификация распространенной пунктуации, ё→е для русского. Грузинские строки сохраняются; альтернативные написания задаются вручную. Не обещать автоматическую транслитерацию и исправление опечаток.
- Несколько поисковых токенов соединяются AND; каждый может находиться в любом индексируемом поле.
- Фильтр дат: два числовых поля «от / до» и готовые периоды из легенды. Слайдер — необязательное улучшение после работающих полей.
- Архитекторы и стили — мультивыбор из справочников. Выбор нескольких архитекторов означает OR; нескольких стилей — OR; группы фильтров соединяются AND.
- Неизвестные даты, неизвестные архитекторы и неклассифицированные стили доступны как отдельные значения соответствующих фильтров.
- Сортировка по названию, возрастанию и убыванию даты. При сортировке дат использовать нижнюю границу принятой датировки; неизвестные и спорные без принятой датировки — в конце в обоих направлениях; при равенстве — название и id.
- Пустой результат объясняет активные условия и предлагает сбросить фильтры.
- Карточка содержит фото, название, дату, стиль и действие «На карте». Каталог доступен с клавиатуры и служит альтернативой управлению геометрией на карте.

Состояние фильтров общее для карты и каталога. При смене вида сохраняются запрос, фильтры и выбранный объект. Если новый фильтр исключил выбранный объект, инспектор закрывается. При смене вида каталога сохранять его прокрутку.

Прямая ссылка на здание при отсутствии других условий не должна неявно наследовать старые локальные фильтры. Неизвестный id дает сообщение и рабочую навигацию, а не падение.

## 5. Датировка и цвета

Не использовать автоматически извлеченный «самый древний год в описании». Дата основания учреждения, первоначального храма, современного корпуса и реставрации — разные сведения.

Для каждого объекта редактор выбирает `mapPhaseId`: этап, который лучше всего характеризует существующее здание. Обычно это завершение строительства нынешнего корпуса; при определяющей облик перестройке может быть выбран ее этап. Решение объясняется в карточке. Остальные этапы сохраняются в истории.

Покраска и фильтр дат используют **одну и ту же принятую датировку выбранного этапа**. Интерфейс называет ее «Дата постройки / формирования нынешнего облика» и объясняет правило в справке.

| Годы включительно | Подпись легенды | Цвет, исходное предложение |
|---|---|---|
| До 1799 | До 1800 | #6E40AA |
| 1800–1849 | 1800–1849 | #417DE0 |
| 1850–1899 | 1850–1899 | #1FA187 |
| 1900–1919 | 1900–1919 | #73A942 |
| 1920–1959 | 1920–1959 | #C3A32D |
| 1960–1991 | 1960–1991 | #DB7C26 |
| С 1992 | С 1992 | #C84949 |
| Нет принятой даты | Дата неизвестна / спорная | #858585, пунктирная обводка |
| Диапазон пересекает несколько периодов | Датировка охватывает несколько периодов | #B0B0B0, пунктирная обводка |

Это диапазоны лет, а не буквальные века и не классификация стилей. Палитра должна пройти визуальную проверку на подложке и при симуляции нарушений цветового зрения. Дата всегда есть также текстом; цвет не является единственным носителем информации. При необходимости палитру можно скорректировать централизованно до визуальной приемки, сохранив границы периодов.

Правила датировки:

- Точный год: `minYear = maxYear`.
- Строительство 1902–1905: для карты использовать 1905 как известный год завершения; начало 1902 хранить отдельно и показывать в истории.
- «Около 1900» не превращать в точный 1900. Принятый редактором диапазон должен быть указан явно и обоснован; не вычислять произвольные ±5 или ±10 лет.
- Приблизительная датировка 1895–1905 попадает в несколько периодов: специальный серый цвет с объяснением, а не произвольный выбор среднего года.
- Диапазон внутри одного периода получает цвет этого периода и текстовую пометку приблизительности.
- Противоречащие источники сохраняются. Если редактор принял одну версию, она используется с пометкой и объяснением; иначе дата считается спорной без принятого интервала.

Числовой фильтр дат использует пересечение интервалов: `building.minYear <= filter.to && building.maxYear >= filter.from`. Это означает «принятая датировка хотя бы частично входит в диапазон». Объяснить это рядом с фильтром. Граница «от» или «до» может отсутствовать. Неизвестные/спорные без принятого интервала включены при выключенном фильтре и исключены при числовом фильтре, если пользователь отдельно не выбрал «Включить неизвестные».

При выборе нескольких периодов их интервалы соединяются OR. Если одновременно заданы числовые границы и периоды, сначала пересечь их; пустое пересечение дает пустую выдачу. Семантика не должна различаться между картой и каталогом.

## 6. Контракт данных

Перед началом интерфейса зафиксировать схемы с версией. Авторские данные — JSON; геометрия — GeoJSON RFC 7946. Все координаты в WGS84, порядок `[долгота, широта]`; преобразование к `[широта, долгота]` Leaflet выполняется в одном адаптере.

### 6.1. Building

| Поле | Тип / назначение |
|---|---|
| id | Стабильный строковый id; не зависит от текущего названия или адреса |
| publicationStatus | draft / reviewed / published; в сайт попадают только published |
| names | Обязательное ru; необязательные ka/en; aliases — массив вариантов |
| address | Отображаемая строка, район, прежние адреса при наличии |
| location | Подтвержденная точка внутри объекта/на его территории, `[lon, lat]` |
| footprintFeatureIds | Ссылки на один или несколько контуров; пусто только при pointOnly |
| geometryQuality | verifiedFootprint / approximateFootprint / pointOnly; источник и пояснение |
| inclusionReason | Краткое объяснение включения и sourceIds |
| mapPhaseId | Ссылка на один из phases; используется для покраски и даты фильтра |
| phases | Этапы construction / rebuild / restoration с датировкой и источниками |
| architectCredits | personId, role, phaseId, attributionStatus, sourceIds |
| styleAssignments | styleId, phaseId, attributionStatus, sourceIds |
| summary | Короткое авторское описание, примерно 400–900 знаков |
| history | Необязательный более подробный текст |
| heritageStatus | Необязательно: статус, идентификатор реестра, sourceIds; не выводить по одному факту старого возраста |
| photoIds | Упорядоченный список фотографий; первая — основная |
| evidence | Привязки утверждений к источникам: путь поля/этап, sourceIds, краткое пояснение |
| reviewedAt | Дата редакционной проверки |
| editorialNotes | Внутренние заметки; не включаются в публичную сборку |

### 6.2. Phase и DateEstimate

Каждый этап содержит id, kind, completion, необязательный `constructionStartYear`, описание и sourceIds.

`completion` содержит:

- `status`: accepted / unknown / disputed;
- `precision`: exact / range / circa / century / unknown;
- `minYear`, `maxYear`: целые числа или оба null;
- `display`: человеческая запись, например «Конец XIX — начало XX века»;
- `sourceIds` и `note`: основание принятой интерпретации;
- `alternatives`: альтернативные датировки с отдельными sourceIds, если источники расходятся.

`accepted` требует обоих числовых значений и `minYear <= maxYear`. `unknown` и `disputed` без принятой версии требуют null. Если одна версия принята с оговоркой, статус accepted, оговорка и альтернативы сохраняются. Для точного года границы равны.

### 6.3. Справочники и связанные сущности

- **Architect:** id, names ru/ka/en, aliases; годы жизни необязательны. Один человек с разными написаниями — одна запись. Не заводить фиктивного архитектора с id unknown: отсутствие подтвержденного авторства кодируется отсутствием принятого credit.
- **ArchitectCredit:** архитектор, роль original / rebuild / restoration / engineer / attribution; статус confirmed / attributed / disputed. Фильтр архитекторов MVP включает confirmed и attributed для исходного строительства и определяющей облик перестройки; реставраторы и инженеры видны в истории, но не смешиваются с авторами. Спорные credits не попадают в обычный фильтр. Это правило вынести в одну функцию.
- **Style:** id, русское название, aliases, короткое определение. Допускать несколько стилей и значение «не классифицирован». Фильтр использует принятые стили выбранного mapPhaseId; исходный стиль утраченного корпуса не должен подменять текущий.
- **Photo:** id, buildingId, локальный путь к включенной производной, width/height, caption, alt, creator, sourcePageUrl, licenseId, licenseUrl, attributionText, modifications. Каждая фотография явно связана со зданием; городской вид без узнаваемого объекта не заменяет фото здания.
- **Source:** id, title, url или библиографическая запись, publisher/author, accessedAt, page/section, применимые условия использования, необязательная короткая заметка. Источник текста и лицензия фотографии — разные сущности.
- **Geometry source:** исходный набор, лицензия, дата извлечения, исходный OSM id или иной id, способ привязки и ручные правки. Сохранять отдельно от исторических утверждений.

### 6.4. Геометрия

`footprints.geojson` содержит FeatureCollection с Polygon/MultiPolygon. У feature обязательны уникальный id и `properties.buildingId`. Полная карточка не дублируется в properties.

У комплекса может быть несколько контуров с одним buildingId. Щелчок по любому открывает ту же карточку; счетчики считают здания, а не геометрии. Несколько частей одного комплекса с самостоятельными датировками и значением могут быть отдельными объектами, связанными `complexId` — только по явному редакционному решению.

Не рисовать выдуманный прямоугольник вместо неизвестного контура. При отсутствии надежной геометрии использовать точку и пометку «Точный контур не установлен». Для MVP минимум 40 из 50 объектов должны иметь проверенные контуры; остальные — честные точечные объекты. Все 50 должны иметь проверенное положение.

### 6.5. Автоматическая валидация

Сборка завершается ошибкой при нарушениях схемы, дублирующихся id, несуществующих ссылках, неправильном порядке дат, отсутствии выбранного этапа, невалидных координатах/полигонах, геометрии вне объявленного покрытия, отсутствующих медиафайлах, неописанных правах фотографии, опубликованной карточке без источника и причины включения.

Проверять соответствие location контуру с учетом объявленного допуска и комплексов; крупные несовпадения — ошибка, пограничные — отчет на ручную проверку. Координаты не исправлять автоматически перестановкой осей.

Отдельно выводить отчет полноты: сколько неизвестных дат и архитекторов, точечных объектов, карточек с одной фотографией, спорных атрибуций. Такие случаи не маскируются, но сами по себе не запрещают релиз.

## 7. Откуда брать сведения и как их проверять

### 7.1. Источники-кандидаты

1. Национальный портал культурного наследия Грузии: карточки, идентификаторы, географические данные. Портал описывает единую базу и пространственные данные [S1]. Наличие нужных полей, реальную выгрузку и разрешение на переиспользование необходимо проверить на пилоте; существование портала не доказывает полноту дат, наличие контуров и открытость фотографий.
2. Издания по архитектуре Тбилиси, архивные материалы, сайты музеев и учреждений, научные публикации. Для книг указывать страницу. Предпочитать конкретный источник по зданию общему туристическому описанию.
3. OpenStreetMap — кандидат на геометрию и подложку. Это не авторитетный источник архитектора и даты. Атрибуция и условия ODbL обязательны [S2].
4. Wikimedia Commons — кандидат на фотографии. Проверять страницу каждого файла, автора, лицензию и условия производных изображений [S3]. Собственные фотографии также подходят при явно зафиксированных правах.
5. Wikidata/Wikipedia допустимы для поиска кандидатов, алиасов и ведущих к первоисточникам ссылок. Автоматически не считать их значения проверенными.

Официальные API и скачивание внешних материалов допустимы **на этапе подготовки данных**, не во время использования сайта.

### 7.2. Редакционный процесс

1. Собрать кандидатов с основанием включения и ссылками.
2. На десяти объектах проверить доступность информации, фотографии, геометрию и процесс лицензирования.
3. Сопоставить название, адрес, фото и координаты: одинаковый адрес или название учреждения не гарантируют тот же корпус.
4. Подтвердить ключевые утверждения источниками. Для спорных дат/авторства искать независимый второй источник. «Два сайта, копирующих один текст» не являются независимым подтверждением.
5. Разделить этапы постройки и перестроек; выбрать mapPhaseId.
6. Написать короткое собственное описание без копирования абзацев.
7. Проверить фотографии и сохранить разрешенные производные локально с атрибуцией.
8. Проверить карточку редактором и только затем перевести в published.

Модели могут собирать черновики и предлагать интерпретации. Не подтвержденные сведения остаются unknown/draft. Не устанавливать дату и архитектора по внешнему виду. Не заполнять пропуски правдоподобными именами. Если исполнитель не имеет доступа к источнику, он сообщает, что именно не проверено; выдуманная ссылка недопустима.

### 7.3. Лицензии и происхождение

- Не использовать изображения из произвольной выдачи поиска, Google Maps и Street View как готовые материалы сайта.
- Для каждого фото хранить точную лицензию и версию, автора, ссылку на исходную страницу, сведения об обрезке/цветокоррекции. Соблюдать условия конкретного файла; открытый просмотр изображения сам по себе не дает права перепубликации [S3].
- Наборы геометрии на основе OSM хранить отдельно, документировать изменения и распространять с требуемыми сведениями об ODbL; включить страницу атрибуции и необходимые материалы/ссылки для выполнения применимых условий [S2]. Раздельное хранение не является автоматическим освобождением от лицензии производной базы.
- Разделить лицензирование кода, редакционного текста, геометрии и фотографий; не ставить одну общую MIT-лицензию на все содержимое.
- Не скачивать массово стандартные тайлы tile.openstreetmap.org для автономного пакета: такая предварительная загрузка запрещена политикой сервиса [S4]. Использовать допустимый исходный векторный набор или источник с явно разрешенной упаковкой.

## 8. Техническая архитектура

### 8.1. Рекомендуемый стек

| Часть | Решение |
|---|---|
| Приложение | TypeScript + React + Vite |
| Карта MVP | Leaflet, прямое подключение через один React-адаптер |
| Геоданные | Локальные GeoJSON; Leaflet поддерживает их и стилизацию объектов [S5] |
| Отрисовка | Canvas для плотной фоновой геометрии; SVG для небольшого интерактивного слоя зданий |
| Состояние | React reducer/context; без отдельного глобального хранилища до появления необходимости |
| Схемы | Zod; один контракт для проверки входных JSON и вывода TypeScript-типов |
| Подготовка | Node/TypeScript-скрипты; сложная ГИС-обработка при необходимости отдельной воспроизводимой утилитой |
| Тесты | Vitest для логики и валидаторов; Playwright для сценариев браузера |
| Стили | Обычный CSS с переменными; без обязательной UI-библиотеки |
| Зависимости | Совместимые стабильные версии, зафиксированные lockfile; не использовать prerelease без причины |

Leaflet выбран для небольшой конечной векторной карты, а не как оболочка для онлайн-тайлов. MapLibre не требуется для 50 объектов и ограниченной подложки; перенос на другой движок возможен позже после замеров и отдельного решения.

Vite создает сборку для статического хостинга [S6]. Не нужны Next.js, SSR, Postgres, Supabase, Firebase, серверный Elasticsearch и серверные функции.

### 8.2. Самодостаточная подложка

Для MVP заранее подготовить конечные слои:

- река и водоемы;
- основные улицы и достаточно второстепенных улиц для ориентации;
- парки и крупные общественные пространства;
- небольшое число районов, площадей и других ориентиров;
- контуры обычных домов — необязательно, только если они помогают чтению и помещаются в бюджет.

Подложка нейтральная, не должна конкурировать с цветами зданий. Она позиционируется как схематическая карта атласа, не автомобильный навигатор.

В T01 зафиксировать `coverage.geojson`, диапазон масштабов и правила детализации. Подложка покрывает все опубликованные объекты и запас вокруг них. Начальный вид показывает исторический центр; отдаленные включенные объекты доступны через каталог и кнопку общего охвата.

Геометрию обрезать по покрытию, упростить с сохранением топологии и подготовить максимум два уровня детализации. Оба загружаются заранее. Переключение по масштабу выполняется в памяти. Контуры самих зданий атласа не упрощать настолько, чтобы терялись дворы и узнаваемая форма.

Подписи рисовать локальным текстом/DivIcon, использовать системный шрифт или заранее загруженный шрифт. Не использовать URL тайлов, внешние glyph-серверы, CDN-иконки и стандартные marker icons с незагруженными PNG. Для маркеров подходят CircleMarker и собственные встроенные значки.

Пилот на десяти объектах обязан подтвердить, что такая карта удобна для ориентации. Если качество или объем неприемлемы, зафиксировать проблему и конкретную альтернативу; не подменять без согласования требование внешними тайлами.

### 8.3. Поток данных

Подготовка: источники → черновики → редакционная проверка → валидируемые JSON/GeoJSON → оптимизация фото/подложки → публичный пакет → dist.

В браузере: bootstrap → загрузка пакета → проверка версии/целостности → локальные индексы и Blob URL фотографий → ready → карта, каталог и инспектор работают только с загруженными данными.

Сборка выпускает `atlas-manifest.json` с версией, перечнем обязательных ресурсов, размерами и контрольными суммами. Включать данные, фоновые слои, все варианты фото, если их несколько, и прочие ресурсы приложения. Манифест не включает самого себя. Его генерация должна быть автоматической, а не ручным списком.

Все сетевые ресурсы загружаются до ready с ограниченным параллелизмом, например 4–6 запросов. Фотографии сохраняются в памяти как сжатые Blob и показываются через Blob URL. `loading=lazy` может откладывать декодирование/отрисовку, но не первоначальное получение включенных изображений. Не полагаться на неуправляемый HTTP-кэш браузера как единственную гарантию.

После ready запрещены динамическая загрузка экранов, обращение за новой порцией JSON, исходниками фото или картографическими данными. Импорты экранов статические. Предварительная загрузка должна учитывать CSS-ресурсы; итог проверяется сетевым тестом.

Не декодировать одновременно все полноразмерные фото: держать сжатые данные, а не сотни растров в памяти. Освобождать ненужные декодированные изображения; Blob URL живут столько, сколько пакет открыт, и отзываются при его выгрузке/замене.

### 8.4. Состояние и ссылки

Один `AppState`: view, query, dateFilter, architectIds, styleIds, sort, selectedBuildingId, camera. Единственная функция вычисления результата используется картой и каталогом.

Для ссылок использовать hash-параметры, например `#view=map&building=<id>`. Схема поддерживает сериализацию фильтров, вида и камеры без серверных rewrite-правил. Параметры сортировать и валидировать; неизвестные значения игнорировать с безопасными значениями по умолчанию.

Открытие/закрытие карточки и смена вида отражаются в истории осмысленно; перемещение карты обновляет адрес через replace с задержкой, не создает десятки шагов Back. Не выполнять сетевую навигацию при переходе между представлениями. Все файловые пути совместимы с размещением под `/atlas/`, а не только в корне домена.

### 8.6. Размер и производительность

Начальные бюджеты для пилота, затем один пересмотр по реальным замерам:

- полный начальный пакет для 50 зданий: цель ≤40 MiB передаваемых байтов;
- подложка и геометрия: цель ≤5 MiB после HTTP-сжатия;
- начальный JS: цель ≤500 KiB gzip;
- по 1–2 фотографии на объект, длинная сторона до 1200 px, обычно 120–250 KiB на фотографию; WebP подходит для MVP;
- никаких оригиналов по 10–30 MB и скрытой кнопки загрузки незапакованного оригинала;
- локальная фильтрация 150 объектов: вычисление результата ≤100 ms на зафиксированном тестовом устройстве;
- после ready открытие карточки реагирует сразу, без сетевого ожидания; фотография может кратко декодироваться.

40 MiB на канале 10 Mbit/s — уже примерно 34 секунды только на передачу, без учета накладных расходов. Поэтому не обещать «весь автономный атлас за секунду». Показывать объем и прогресс. На реальном пилоте сначала уменьшать фотографии и подложку, а не незаметно возвращать ленивую сетевую подгрузку.

Отчет производительности фиксирует устройство, браузер, канал, объем, время до ready и использование памяти. Нельзя честно определить универсальные секунды загрузки без условий измерения.

T12 допустимо готовить партиями по 10, но итоговый набор принимает один редактор. Это возможности организации работ, не необходимость одновременно запускать множество исполнителей.

### Контрольные точки

**G1 — перед интерфейсом:** T01–T03. Приняты данные десяти объектов, модель фаз, права фото и способ получения геометрии. Если материалов нет, не маскировать это красивым UI на вымышленных карточках.

**G2 — вертикальный прототип:** T04–T09 на десяти объектах. Уже работает весь путь «загрузка → карта → клик → реальные фото», в том числе без сети. Здесь проверить читаемость подложки и бюджет, прежде чем расширять контент.

**G3 — функциональный MVP:** T10–T11. Два вида, единые фильтры и прямые ссылки на пилоте.

**G4 — релиз:** 50 объектов и T13. Полная редакционная и техническая приемка. Публикация на хостинге — отдельное действие после готового dist; сам этот документ не поручает ничего публиковать.

## 10. Проверки, которые нельзя пропустить

### 10.1. Главный сетевой тест

Проверять production build, не Vite dev server с HMR.

1. Открыть сайт в чистом браузерном контексте без ранее наполненного кэша и service worker.
2. Записать все запросы с начала загрузки; внешних доменов в обязательной загрузке быть не должно.
3. Дождаться явного ready; сохранить границу измерения и число сетевых обращений.
4. Запретить дальнейшие HTTP/HTTPS-запросы и включить offline в браузерном контексте.
5. Пройти все поддерживаемые масштабы и области покрытия, открыть каждый объект, показать каждую фотографию, перейти между видами, выполнить поиск, все виды фильтрации и Back/Forward.
6. Проверить не только отсутствие успешных ответов, но и **отсутствие попыток** новых сетевых запросов после ready. HTTP-кэш и неудачные запросы не должны маскировать нарушение. При проверке отличать HTTP/HTTPS от локальных blob/data URL.
7. Убедиться, что изображения реально загрузились (`naturalWidth > 0`), карта и карточки не показывают заглушки вместо обязательных материалов.

Этот тест — критерий архитектуры, а не необязательная оптимизация.

### 10.2. Предметные тесты

- Границы периодов: 1799/1800, 1849/1850, 1899/1900, 1919/1920, 1959/1960, 1991/1992.
- Строительство 1902–1905 окрашено по принятому завершению, а не случайно по началу.
- Интервал 1895–1905 имеет специальную окраску и находится фильтрами, пересекающими его с любой стороны.
- Приблизительность, отсутствие даты и конфликт источников дают разные понятные подписи.
- Выбор нынешнего корпуса не теряет сведения о старом и не окрашивает современный корпус по дате основания учреждения.
- Несколько авторов, алиасы одного автора и разные роли не дают дублирующихся карточек.
- Несколько контуров одного здания считаются как один объект.
- Комбинации OR внутри групп и AND между группами дают одинаковый набор id на карте и в каталоге.

### 10.3. Браузерные сценарии

- Клик по контуру, точке и результату поиска открывает один и тот же правильный инспектор.
- Прямая ссылка и обновление страницы по ней работают на статическом хостинге и в подкаталоге.
- Закрытие инспектора сохраняет камеру; «На карте» показывает объект с учетом панели.
- Пустая выдача и битые параметры URL не ломают приложение.
- Ширины 360, 768 и 1440 px; панель не закрывает все управление, карта корректно пересчитывает размер после изменения раскладки.
- Клавиатура: навигация каталога/фильтров, открытие карточки, Escape, видимый фокус. Мобильная модальная панель удерживает фокус; немодальная боковая панель не блокирует остальной интерфейс.
- Контраст текста и управляющих элементов; даты читаются без различения цветов. У фото есть содержательный alt. Анимации учитывают prefers-reduced-motion.
- Финальная проверка в актуальных стабильных Chromium, Firefox и WebKit; версии записать в отчете. Дополнительно ручная проверка на доступном телефоне.

### 10.4. Данные и поставка

- Ни одной опубликованной карточки с непроверенным совпадением адреса/корпуса.
- Нет фото без автора/лицензии или разрешения, если оно необходимо.
- Описания не являются скопированными чужими абзацами.
- Данные и геометрия не расходятся; все опубликованные объекты входят в покрытие.
- Ресурсный аудит не находит внешние fonts/images/tiles/API и незапакованные пути.
- `check` запускает типизацию, валидацию данных и необходимые unit-тесты; `build` создает пакет; `test:e2e` проверяет готовый dist.
- README объясняет установку, сборку, локальный статический просмотр, добавление объекта, обновление фотографий и лицензий.

## 11. Правила передачи задач более слабым моделям

### Универсальный стартовый запрос

> Реализуй только задачу TXX из приложенного плана архитектурного атласа Тбилиси. Сначала прочитай актуальные docs, схемы данных и существующий код. Используй принятый стек и сохраняй контракт данных. Выполни входные условия, внеси минимально необходимые изменения, запусти указанные проверки. Не заменяй неизвестные исторические сведения вымышленными и не подключай внешние сервисы во время работы сайта. Если задача требует менять контракт или не может быть выполнена на доступных материалах, опиши конкретное препятствие; независимую разрешенную часть доведи до рабочего результата. В конце перечисли измененные файлы, поведение, результаты проверок и оставшиеся ограничения.

К каждому заданию отдельно приложить:

1. Его точный вход и ожидаемый результат из таблицы T01–T13.
2. Только принятые версии документов и файлов; не смешивать несколько противоречивых вариантов схем.
3. Образец результата предыдущей задачи и точные команды проверки.
4. Условия завершения; что явно остается за рамками этой задачи.

Правила для исполнителей:

- Не переписывать проект целиком ради локальной задачи.
- Не менять идентификаторы объектов и справочников ради косметики.
- Не добавлять зависимости «на будущее».
- Не править сгенерированные данные вручную; исправлять источник и пересобирать.
- Не утверждать «проверено» без реально выполненной проверки; при отсутствии среды указать, что осталось непроверенным.
- Не выдавать моковые фотографии и синтетические карточки за реальные. Тестовые fixtures отделены от публичного каталога и никогда не попадают в релиз.
- Изменения контрактов сначала отражать в decisions и data-contract, затем в коде и проверках.
- После каждой задачи передавать короткую записку следующему исполнителю: какие контракты действуют, какие команды проходят, какой следующий шаг готов.

## 12. Риски и заранее выбранные реакции

| Риск | Реакция |
|---|---|
| Недостаточно достоверных сведений | Оставить поле неизвестным или объект в draft; уменьшить опубликованный набор с явным отчетом, не выдумывать факты |
| Реестр дает только точки | Проверить контур по другому допустимому источнику либо показать точку; не выдавать ее за точную форму здания |
| Недостаточно разрешенных фото | Найти другой разрешенный материал/собственную съемку; до этого не считать карточку готовой к релизу |
| Несовместимые условия перепубликации | Заменить материал или отложить объект; не считать публичность сайта разрешением на упаковку |
| Пакет слишком большой | Сжать фото, убрать дубликаты, уменьшить фоновые данные и число включенных ракурсов; объем контента менять явно |
| Схематическая карта плохо читается | Улучшить улицы, ориентиры и подписи на пилоте; не расширять каталог до подтверждения качества |
| Отдаленные объекты сильно раздувают покрытие | Детальная подложка для центральной зоны и упрощенная для общего охвата, обе заранее загружены |
| Старые и новые этапы путаются | Обязательный mapPhaseId и явное пояснение принятой даты |
| Перезапуск браузера без сети не работает | Это вне гарантии MVP; не называть открытый в памяти пакет полноценным установленным offline-приложением |

## 13. Что можно сделать после MVP

1. Расширение до 100–150 объектов только после проверки размеров, источников и редакционного процесса.
2. Полноценная автономная повторная загрузка: service worker, версионированный кэш всего пакета, проверка квоты, атомарное обновление и откат. Service worker требует соответствующего безопасного контекста; необходимо отдельно тестировать потерю/вытеснение браузерного хранилища [S7]. Фоновые обновления не должны нарушать обещание отсутствия сетевых обращений без отдельного согласованного поведения.
3. Переводы интерфейса и карточек на грузинский/английский.
4. Тематические подборки и прогулки, собранные редактором.
5. Более подробная картография. PMTiles пригоден для статического хранения карты, но обычное чтение делает HTTP Range-запросы по мере просмотра [S8]. Поэтому простая замена GeoJSON на размещенный PMTiles **не выполняет** строгий режим без запросов; для него потребуется заранее получить архив целиком и читать его из локального хранилища.

## 14. Условие готовности проекта

Проект готов, когда человек открывает статический сайт, дожидается загрузки конечного пакета, отключает сеть, исследует карту Тбилиси, находит здания фильтрами и смотрит все включенные фотографии и сведения. Все опубликованные объекты прошли проверку происхождения фактов, геометрии и изображений. Новому исполнителю достаточно репозитория и README, чтобы повторить сборку и добавить следующую проверенную карточку.
