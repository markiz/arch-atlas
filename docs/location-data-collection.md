# Сбор данных для новой локации

Рабочее руководство для агента, добавляющего город или поддерживающего данные архитектурного атласа. Сверено с кодом и локальными файлами 1 ноября 2026 года. Источник Place ID — Google API, что подтверждено владельцем проекта в этой сессии. Ниже отдельно обозначены существующая реализация и рекомендуемый порядок для следующего города. Описанные загрузчики не запускались для обновления внешних данных при подготовке документа.

## 1. Результат и границы задачи

Для города собираем отобранные архитектурно значимые здания с реальными контурами, сведениями о постройке, локальными фотографиями и проверяемыми источниками. Для ориентации нужна сдержанная векторная подложка, покрывающая город и пространство между объектами. Массовое включение обычных домов и посторонних POI ради плотности запрещено. Исторический жилой дом допустим при обоснованной ценности.

Батуми и Кутаиси сейчас имеют только пустое состояние в переключателе. Создание набора для них требует исследования и подключения в приложение; готового универсального импортера городов нет. Нельзя подменять Тбилиси данными другого города в существующих общих файлах.

Полнота и редакционная проверка — разные характеристики. Отсутствие даты, архитектора или фотографии допустимо в исследовательской карточке при честном обозначении пробела. Отсутствие реального Polygon/MultiPolygon не допускается для публикуемого объекта атласа. Такой кандидат остаётся в исследовательских материалах.

Для продолжения набора Тбилиси подготовлена очередь из 200 кандидатов в [исследовательском отчёте](research-next-200.md). Исходный снимок был составлен до добавления проверки пересечений: в нём ещё возможны дубли. Существующий отчёт защищён от перезаписи; `--force` создаст новый отбор, который может не соответствовать сохранённым Google-результатам и заметкам. Сохраняются только ID, ссылки и признаки заполненности; текст реестра в отчёт не копируется, поскольку условия повторного использования не установлены. Автоматическая близость точки и контура не подтверждает идентичность здания. Нужна ручная проверка каждого кандидата.

## 3. OSM и Overpass: рациональный способ получения геоданных

**Источник — OpenStreetMap. Overpass — инструмент выборки из OSM, а не другая карта.** Он позволяет запрашивать только нужные категории в заданной области. Для нового города рекомендуем отбор по административной границе с проверенным OSM ID, а не по одному названию города. См. [описание Overpass](https://wiki.openstreetmap.org/wiki/Overpass_API) и [фильтр по области](https://dev.overpass-api.de/overpass-doc/en/full_data/area.html).

Рекомендуемый процесс проекта:

1. Установить административную границу, её OSM relation ID и область подробного покрытия. Сохранить выбранные значения, а не повторять неоднозначный поиск по названию при каждой сборке.
2. Отдельно получить кандидатов с историческими/охранными тегами и отдельными запросами — разрешённые слои подложки. Здания атласа и ориентиры подложки не считать одной коллекцией.
3. Для конкретных кандидатов догружать полные контуры, включая узлы, составные пути и роли членов отношений. Не заменять контур результатом `center`. Проверять полноту данных после пространственного отбора.
4. Сохранять текст запроса, endpoint, параметры, время загрузки UTC, время базы OSM из ответа и сам ответ в `raw/`. Большие выборки делить на небольшие тематические запросы; повторять временные ошибки с задержкой, использовать сохранённые ответы при пересборке.
5. Преобразовать выбранные элементы в локальный GeoJSON. Не включать всю городскую застройку «на всякий случай»; полный слой обычных зданий добавлять только по явному запросу как отдельную категорию.

Синтаксис запроса и геометрический вывод описаны в [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL). Запросы нового города нужно сохранить вместе с загрузчиком; нижеописанный старый XML-загрузчик не заменяет такой процесс.

### Как это сделано сейчас

`scripts/fetch-osm.py` использует основной OSM API: `GET https://api.openstreetmap.org/api/0.6/map?bbox=west,south,east,north`. Для Тбилиси зашита сетка 4×4: долгота 44.783–44.811, широта 41.687–41.711, шаги 0.007 и 0.006 градуса. Ответы записаны в 16 `raw/osm-grid-*.xml`. Существующий файл больше 1000 байт считается кэшем без проверки свежести; максимум три потока, timeout 60 секунд. Успешное завершение программы само по себе не подтверждает, что загружены все участки: ошибки печатаются отдельно.

Эти XML содержат и обычные здания центральной зоны. Сборщик сохраняет их в `kind=building` в отдельный `public/atlas/building-outlines.geojson`; основная подложка `basemap.geojson` содержит дороги, воду, зелёные зоны и ориентиры. Файл обычных контуров проверяется и включается в манифест сборки, но приложение загружает его только при включении слоя «Силуэты зданий». Это наследие текущей выборки, не требование расширять городской слой домов.

`raw/osm-tbilisi-selected.json` — ответ Overpass с выбранными улицами, зелёными зонами и музеями. В заголовке сохранены версия генератора и время базы OSM. **Текст исходного запроса и отдельный загрузчик этой выборки в репозитории не найдены.** Нельзя заявлять, что её получение уже воспроизводится одной командой.

#### Диагностика Overpass (2026-10-31)

При проверке `https://overpass-api.de/api/interpreter` вернул HTTP `406` с короткой HTML-страницей nginx, без тела Overpass, `Retry-After` или объяснения причины. Тот же результат получен для простого запроса одной точки, как через GET, так и через POST. Это подтверждает отказ на HTTP-уровне до получения обычного ответа Overpass, но **не позволяет установить причину**: по одному generic 406 нельзя доказать ни rate limit, ни блокировку по заголовкам/сетевому адресу, ни временную настройку сервера. Это не типичный Overpass-ответ с диагностикой лимита; считать запрос гарантированно безопасным для повтора или утверждать, что лимита не было, тоже нельзя.

**Уточнение по `overpass.osm.ch`:** это региональный экземпляр только с данными Швейцарии, не источник для Тбилиси. Прежняя проверка HTTP `200` выполнялась запросом к одному узлу и подтвердила только доступность endpoint; она не проверяла покрытие Тбилиси. В публичной таблице Overpass для этого экземпляра указано «Ask User:Datendelphin», опубликованных численных квот для роботов там нет. Условия SOSM оставляют за оператором право вводить ограничения в любое время. Поэтому не направлять туда запросы по Тбилиси и не предполагать, что отсутствие указанной квоты означает неограниченное использование.

Для глобального основного Overpass в общих рекомендациях проекта указаны ориентиры: для разового использования — менее 10 000 запросов и менее 1 GB скачивания в сутки суммарно, с общим временем обработки не более 10 минут; для регулярно работающего приложения эти ориентиры предлагается уменьшить в 100 раз. Не запускать параллельные скрипты, кешировать результаты и использовать региональные выгрузки для больших объёмов. При `406` или `429` документация просит выдержать паузу не менее 30 секунд; повторять запрос только после паузы и без автоматического цикла. Эти общие рекомендации не являются опубликованной квотой для `overpass.osm.ch` или гарантией доступности. Перед массовой выгрузкой лучше уточнить допустимый разовый объём у оператора выбранного экземпляра.

#### Где брать OSM для всей территории Тбилиси

Для разовой городской выборки предпочтителен региональный файл, который обрабатывается локально, а не серия запросов к публичному Overpass:

- [Geofabrik: Georgia](https://download.geofabrik.de/europe/georgia.html) публикует полный `.osm.pbf` страны с данными OSM. Скачать один PBF и выполнить географическое ограничение, извлечение зданий и сбор зависимостей локально. Не брать бесплатные Shapefile/GeoPackage Geofabrik как источник полных контуров: это подготовленный ограниченный набор слоёв, а не полный OSM. Страница Geofabrik указывает актуальность конкретного файла; сохранять её timestamp и checksum рядом с исходником.
- [BBBike custom extracts](https://extract.bbbike.org/extract.html) позволяет нарисовать прямоугольник или полигон, задать область и скачать PBF, GeoJSON и другие форматы. Сервис сообщает об ежедневном обновлении данных и обработке обычной заявки примерно за 2–7 минут; действует fair-use policy, но численная частота запросов публично не установлена. Для одного небольшого экстракта пользоваться формой один раз, не автоматизировать повторные заявки.

Для воспроизводимой подготовки в проекте предпочтителен Geofabrik PBF: записать URL, дату загрузки, timestamp исходных данных и контрольную сумму, затем локально вырезать область административной границы Тбилиси и нужные геометрии. BBBike удобен, если нужен готовый экстракт по нарисованному полигону; сохранить его параметры/контур и метаданные источника, так как получение через форму не является сборкой проекта. В обоих случаях сверить покрытие по всей границе и проверить реальные Polygon/MultiPolygon, а не точки/центроиды. Источник предоставляет OSM-данные по ODbL; сохранять требуемую атрибуцию OpenStreetMap.

По прямому запросу на контуры по всему Тбилиси 2026-10-31 скачан `georgia-latest.osm.pbf` с Geofabrik и локально обработан скриптом `scripts/extract-tbilisi-building-outlines.py`. Использована административная граница `relation/1996871` (`admin_level=4`); выборка включает замкнутые OSM ways с тегом `building=*`, чья внутренняя точка находится внутри границы. Получено 121 313 контуров; 115 531 добавлен в подложку после устранения повторов с центральной XML-сеткой. Незамкнутый/невалидный контур пропускается, контуры не подменяются точками. Выход — `raw/osm-tbilisi-building-outlines.geojson` (~41 MB); в поле `source` записаны URL, SHA-256 PBF, timestamp OSM и ID границы. Сам PBF (~98 MB) в репозитории не хранится; для повтора скачать его по URL Geofabrik и выполнить:

```sh
# В образе из Dockerfile и Dockerfile.deepseek Pyosmium, Shapely и Pillow уже
# установлены пакетами apt, а system pip в Debian 12 заблокирован (PEP 668).
python3 scripts/extract-tbilisi-building-outlines.py georgia-latest.osm.pbf
python3 scripts/build-data.py   # только подложка и контуры зданий
npm run build                   # упаковка карточек, манифест и dist/
```

`npm run build` включает GeoJSON подложки в манифест; на момент этой выгрузки суммарный размер публикуемых файлов манифеста был около 65 MB. Актуальный размер смотрите в `public/atlas/manifest.json`, а не в этом историческом абзаце. Для карты сохраняется атрибуция OpenStreetMap.

### Формат исходной карточки

`data/atlas/tbilisi/<id>.json` — pretty-JSON (`indent=2`, UTF-8, завершающий перевод строки). Имя файла совпадает с `id`. Большинство id имеют вид `osm-<номер>`; 10 ранних редакционных карточек сохраняют короткие id (`opera`, `writers`, `imeli`, …), поэтому их файлы называются `opera.json` и т. д. Обязательные поля: `id`, `names`, `addresses`, `descriptions`, `minYear`, `maxYear`, `styleId`, `architectIds`, `districtId`, `yearLabelId`, `coordinates`, `geometry`, `geometryQuality`, `photos`, `source`. Необязательные: `histories`, `osmId`, `originalLanguage`, `otherSource`, `geometryRole`, `geometryVariants`, `googlePlaceId`, `googlePlaceIdSource`.

```json
{
  "id": "osm-1105505029",
  "osmId": "way/1105505029",
  "names": {"ru": "…", "en": "…", "ka": "…", "uk": "…"},
  "originalLanguage": "ka",
  "addresses": {"ru": "…", "en": "…", "ka": "…", "uk": "…"},
  "descriptions": {"ru": "…", "en": "…", "ka": "…", "uk": "…"},
  "histories": {"ru": "…", "en": "…", "ka": "…", "uk": "…"},
  "minYear": null,
  "maxYear": null,
  "yearLabelId": "unknown",
  "styleId": "undetermined",
  "architectIds": [],
  "districtId": "tbilisi",
  "coordinates": [44.7905317, 41.7025608],
  "geometry": {"type": "Polygon", "coordinates": [[[44.7905051, 41.7027021], [44.7906779, 41.7026069], [44.7905317, 41.7025608], [44.7905051, 41.7027021]]]},
  "geometryQuality": "…",
  "photos": [
    "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  ],
  "source": "https://www.openstreetmap.org/way/1105505029"
}
```

`styleId`, `architectIds`, `districtId` и `yearLabelId` — ссылки в городские справочники `aux/<city>/`; подписи на четырёх языках и производные поля (`name`, `style`, `yearLabel`, `architectsByLanguage` и т. п.) подставляет `scripts/assemble-atlas.mjs`, читая `data/aux/<city>.json`. Справочники разделены по видам: `styles.json`, `architects.json`, `districts.json`, `year-labels.json`; каждый — объект `ID -> {source?, labels:{ru,en,ka,uk}}`. `source` необязателен и служит исходной подписью; `labels.ru` — основная русская подпись. `scripts/merge-aux.mjs` проверяет все четыре языка и склеивает файлы в единый `data/aux/<city>.json`. Не храните их в карточке: иначе появится второй источник истины. `minYear`/`maxYear` — либо оба `null`, либо оба целых и `minYear <= maxYear`. `photos` может быть пустым массивом; порядок sha256-идентификаторов задаёт порядок галереи, а полная атрибуция каждого id лежит в sidecar `data/photos/<city>/<sha256>.metadata.json`.

Основной путь — `collect-photo-candidates.py` и `apply-photo-candidates.py`: первый собирает кандидатов в `work/photo-research/candidates.json`, второй сверяет их с `data/photo-gallery-selection.json`, скачивает выбранные снимки и пишет карточки. Точечные `fetch-selected-photos.py`, `fetch-fallback-photos.py`, `fetch-curated-photos.py`, `fetch-curated-remaining.py` и `fetch-conservatory.py` тоже сохраняют проверенное фото в `data/photos/tbilisi/<sha256>.webp`, пишут sidecar и добавляют id в упорядоченный массив `photos`. Затем `npm run photos:thumbs` создаёт недостающие превью 720 px в `data/thumbnails/`; `npm run build` делает это автоматически. `fetch-depicts.py`, `fetch-extra-categories.py`, `fetch-galleries.py` и `fetch-specific-fixes.py` остаются исследовательскими: их промежуточные `data/*.json` сборщик не читает, а удачную находку нужно перенести в карточку вручную. Само появление JSON или WebP не подключает изображение к сайту.

## 5. Как отбираются и обогащаются здания

### Существующая автоматизация

`scripts/research-heritage.py` читает XML-сетку и отбирает только замкнутые `way` с `building`, полным набором узлов и минимум четырьмя координатами. Условия интереса:

- `heritage` равен `1`, `2` или `3`; либо
- `historic` входит в `house`, `building`, `church`, `castle`, `caravanserai`, `hotel`, `monastery`, и есть `wikidata` или `name:ru`.

Исключаются `roof`, `construction`, `garage` и определённые `building:part`. Отношения автоматически в этот список не попадают, а важные здания без этих тегов могут быть пропущены. Поэтому для новой локации обязателен дополнительный редакционный поиск, не только копирование фильтра.

Wikidata загружается через `https://www.wikidata.org/w/api.php`, `action=wbgetentities`, пакетами по 25 QID, с `labels|claims|sitelinks`, языками `ru|ka|en` и тремя попытками. Частичный ответ после ошибок нужно выявлять отдельно.

Новая карточка пишется сразу в `data/atlas/tbilisi/<id>.json`. Старый генератор `build-heritage-extra.py`, который собирал `data/heritage-extra.json` и обрезал набор до 90 записей, удалён: он смешивал автоматический отбор с редакционными правками и зависел от предыдущей публичной сборки. Автоматически можно подготовить черновик фактов и контура, но итоговую карточку с переводами и атрибуцией фото проверяет и сохраняет редактор. `scripts/assemble-atlas.mjs` падает с понятной ошибкой, если в карточке нет обязательных переводов или ссылка (`styleId`, `architectIds`, `districtId`, `yearLabelId`) отсутствует в городском справочнике.

### Требуемая детализация карточки

Контракт задают [типы](../src/types.ts), [упаковщик карточек](../scripts/assemble-atlas.mjs), [проверка исходников](../scripts/validate_cards.py) и [проверка собранных данных](../scripts/check-data.mjs).

В исходном файле не дублируются производные поля: хранятся `names`, `addresses`, `descriptions`, `histories`, `coordinates`, `geometry`, `photos`, `source` и ссылки `styleId`, `architectIds`, `districtId`, `yearLabelId`. Поля `name`, `nameKa/En/Uk`, `address`, `district`, `style`, `yearLabel`, `architects`, `styles`, `districts`, `yearLabels`, `architectsByLanguage` — производные: их подставляет `scripts/assemble-atlas.mjs` для интерфейса из переводов и городского aux-словаря.

| Поле | Что записываем |
|---|---|
| `id` | Стабильный уникальный ID; не менять из-за исправления имени. При нескольких городах обеспечить уникальность во всём приложении |
| `name`, `names`, `nameKa/En/Uk`, `originalLanguage` | Идентичность здания, исторические и современные названия с пояснениями; перевод не служит новым фактом |
| `address`, `addresses` | Реальный адрес; не угадывать номер по соседнему дому. Неподтверждённый адрес обозначать явно |
| `district`, `districtId`, `districts` | Установленный район; автоматические дополнения прошлых волн часто имеют просто «Тбилиси» |
| `minYear`, `maxYear`, `yearLabel`, `yearLabelId`, `yearLabels` | Обоснованный интервал датировки и понятная подпись; при отсутствии данных оба года `null` |
| `architects`, `architectIds`, `architectsByLanguage` | Подтверждённые авторы; если неизвестны — пустые массивы |
| `style`, `styleId`, `styles` | Подтверждённый стиль или «Не определён»; не выводить из внешнего сходства |
| `description`, `descriptions` | Кратко: что это за здание и чем архитектурно интересно; для автоматических карточек честное указание на источник отбора |
| `history`, `histories` | Этапы строительства, перестройки и использования; только подтверждённые сведения |
| `source`, `otherSource` | Прямые страницы, подтверждающие факты; фотостраница хранится отдельно в фотографии |
| `coordinates`, `geometry`, `osmId`, `geometryQuality` | Внутренняя точка, настоящий контур, типизированный OSM ID и честная характеристика проверки |
| `photos[]` | Упорядоченные sha256-идентификаторы нескольких ракурсов, когда они доступны и проверены; допустим пустой массив. Метаданные каждого id — в sidecar |
| `googlePlaceId`, `googlePlaceIdSource` | Необязательная адресная/предметная ссылка Google; не источник датировки или геометрии |

Нынешняя схема имеет только две ссылки на сведения, без доказательств по каждому полю, статуса ручной проверки и даты обращения. До расширения контракта сохранять отдельную исследовательскую записку в `docs/`: ID, поле, утверждение, URL, дата обращения, противоречия, принятое решение. Не добавлять произвольные поля в JSON с ожиданием, что UI их покажет. `draft`, `mapPhaseId`, подробная модель фаз из исходного плана пока не реализованы.

## 6. Контуры, координаты и датировка

В GeoJSON и карточках порядок `[longitude, latitude]`, в Leaflet — `[latitude, longitude]`. Это также порядок входа нового Google-скрипта. Округление OSM-координат при подготовке данных до шести десятичных знаков не означает гарантированную точность измерения.

Первоначальные карточки были собраны старым `build-data.py`: он искал OSM-полигон, содержащий координату Wikipedia, и выбирал наименьший по площади ограничивающего прямоугольника. Сейчас контуры уже лежат в `data/atlas/tbilisi/<id>.json`, а `build-data.py` карточки не трогает. Если контура нет, публиковать точку вместо Polygon/MultiPolygon нельзя.

**Primary-геометрия карточки — надземный след здания**, потому что карта показывает именно его. Официальная граница памятника, relation подземного/составного комплекса и старые way — вторичные контуры: их сохраняем в `geometryVariants` карточки с ролью (`heritage_boundary`, `complex_underground`, `neighbor_wrong_candidate`, `historic_plan`, `visible_domes`); исследовательский снимок для бани №5 остаётся в `data/geometry-variants.json`. Если точного надземного следа нет, допускается fallback на охраняемое ядро: `geometryRole=heritage_boundary`, пунктирная отрисовка и предупреждение в инспекторе, что это не footprint. Relation подземного комплекса на роль footprint не подходит. Если нет и ядра — hold. Пример — баня №5 в [разборе](research-bath-5-geometry.md).

`scripts/resolve-geometries.py` собирает внешние/внутренние кольца через Shapely `polygonize`, `unary_union` и вычитание отверстий. ID отношений ИМЭЛИ, консерватории и театра Руставели зашиты; контур Метехи берётся из `raw/metekhi-way.json`. Скрипт обновляет `geometry`, `osmId` и `geometryQuality` прямо в `data/atlas/tbilisi/<id>.json`. Для новой локации нужен свой проверенный список ID; выполнять старый скрипт без адаптации бессмысленно.

Проверять замкнутость колец, отсутствие пропущенных узлов, самопересечений и нулевой площади, корректность дворов/частей, отсутствие дублей way/relation и принадлежность внутренней точки зданию. Тип Polygon сам по себе не гарантирует геометрическую корректность: штатная JS-проверка её полностью не проверяет.

Автоматической датировки новых карточек в текущем сборщике нет: `minYear`, `maxYear` и `yearLabelId` выбирает редактор. Историческая эвристика автоматических дополнений (удалённый `build-heritage-extra.py`) была такой:

- OSM `start_date`: только точный год 1000–2099 либо дата, начинающаяся с такого года.
- Иначе Wikidata `P571`: недепрекейтнутое значение с точностью минимум до года (`precision >= 9`), год больше 300.
- Иначе `minYear=maxYear=null`, `yearLabel='Не установлена'`. Приблизительные строки и века автоматически не интерпретируются.

Это описание старой эвристики, не гарантия, что `P571` относится к постройке. Редактор уточняет, датируем ли существующий корпус, открытие, начало работ или более ранний храм. Например, у оперы подпись «1880–1896», а числовая датировка — 1896; это дата завершения, а не автоматически скопированный диапазон работ. Для VI века допустим интервал 501–600. При расхождении источников сохранять неопределённость, как в карточке синагоги.

Периоды и цвета общие для карты и каталога: до 1800, 1800–1849, 1850–1899, 1900–1919, 1920–1959, 1960–1991, с 1992. `src/domain.js` назначает цвет только если весь интервал в одном периоде; пересечение периодов даёт нейтральный цвет, неизвестная дата тоже нейтральна. Не придумывать точный год ради цвета.

## 7. Фотографии и переводы

`fetch-sources.py`, `fetch-more.py`, `fetch-more-2.py` запрашивают Wikipedia REST summary по зашитым названиям статей, сохраняют ответ и ищут изображение Commons. Далее Commons API `action=query`, `prop=imageinfo`, `iiprop=url|extmetadata` возвращает URL и метаданные. Эти скрипты создают промежуточные `raw/wikimedia-*.json`; автоматической сборки карточек из них нет.

`fetch-galleries.py` использует `P18` и `P373` Wikidata и ручные категории первоначальных зданий. Категория ограничена 12 файлами, отбираются до четырёх кандидатов, затем до двух на объект. По названиям исключаются карты, планы, логотипы, гербы, портреты и т. п.; это грубый фильтр, не визуальная проверка. Скрипт рассчитан на определённое состояние исходного списка: повторный запуск после расширения может упасть на `manual[b['id']]`.

`fetch-depicts.py` ищет Commons файлы с `haswbstatement:P180=QID`; `fetch-extra-categories.py` расширяет конкретные категории; `fetch-curated-photos.py`, `fetch-curated-remaining.py`, `fetch-conservatory.py`, `fetch-specific-fixes.py` используют вручную заданные имена файлов. Первые три из этой группы (кроме `fetch-specific-fixes.py`) пишут найденное фото прямо в карточку; исследовательские результаты `fetch-depicts.py` и `fetch-extra-categories.py` требуют ручного переноса. `inspect-commons-categories.py` — исследование категорий, не часть сборки.

Перед включением снимка открыть его и сопоставить фасад, корпус, окружение и адрес. Два разных файла одного кадра не считать двумя ракурсами. Страница категории может включать интерьеры, соседние здания и памятники. На современной фотографии может быть новая постройка на историческом месте.

**Основной конвейер галерей** — `scripts/collect-photo-candidates.py` и `scripts/apply-photo-candidates.py`. Первый собирает кандидатов, ничего не записывая в карточки: P180/P18 из Wikidata, тег `wikimedia_commons` из OSM, файлы по улице и номеру дома, по выразительному названию и, в последнюю очередь, по координатам. Поиск идёт через HTML-страницу `Special:Search` (кэш в `work/photo-research/`), потому что тяжёлый `generator=search` API регулярно отвечает HTTP 429; метаданные запрашиваются пакетами через `imageinfo`. Название файла — только гипотеза: адрес проверяется по категориям файла, и категория с другим номером дома на той же улице отклоняет кандидата. Результат — `work/photo-research/candidates.json`.

Второй скрипт скачивает выбранные снимки, применяет лимиты ширины, убирает точные и почти-совпадающие дубли по SHA-1 и perceptual hash, добивает галерею до трёх фотографий, ставит свободные снимки перед fallback реестра и пишет карточки. Файлы сохраняются по SHA-256, поэтому вместо физического переименования меняется только порядок id в `photos`; отчёт — `work/photo-research/applied.json`. После него `npm run photos:source-tags` переносит в sidecars категории Commons как `sourceTags` (для новых снимков основной конвейер пишет их сразу), `npm run photos:review-sheets` готовит листы по 6 фото, модель **за один проход** выбирает content- и quality-теги по чеклисту `docs/photo-review-checklist.md`, а `npm run photos:apply-tags` записывает готовый батч. Автоматического классификатора нет: скрипт только нарезает листы и применяет решения модели. Затем `npm run photos:thumbs` создаёт превью; `npm run build` запускает превью автоматически. Точечные `fetch-*.py` остаются для отдельных батчей, но новый материал следует проводить через этот конвейер.

Текущая обработка использует Pillow: уменьшение только по ширине и без увеличения — до **1920 px** для свободных лицензий и до **1200 px** для неизвестных/коммерческих источников. RGB WebP, quality 80–82. Для Commons нельзя запрашивать оригинал или произвольную ширину миниатюры: Wikimedia отвечает 429/400 и разрешает только стандартные шаги 20/40/60/120/250/330/500/960/1280/1920/3840 px. Поэтому берётся наибольший стандартный размер, не превышающий ширину оригинала; `scripts/upgrade-photo-sources.py` (`npm run photos:upgrade`) использует именно такие URL и не растягивает изображение. Это лимит публикации, а не требование выдавать маленький оригинал за изображение такого разрешения: если источник меньше, файл остаётся исходного размера. Полный файл сохраняется в `data/photos/<city>/<sha256>.webp`, метаданные — рядом в `<sha256>.metadata.json`; `width` и `height` в sidecar — фактические размеры этого WebP, их синхронизирует `scripts/sync-photo-dimensions.py`. Превью генерируется отдельно в `data/thumbnails/<city>/<sha256>.webp`: то же имя, ширина до **720 px**, пропорции сохраняются, без увеличения; `data/thumbnails/` не хранится в Git. Превью не пересоздаются, если исходник не новее готового файла.

Каждый sidecar содержит `author`, `license`, `licenseUrl`, `source`, `modifications`, `width`, `height`; `description`, `sourceTags` и `visualTags` необязательны. `sourceTags` — сырые категории источника, `visualTags` — стандартизованные оптические теги из `data/photo-visual-tags.json` (43 тега: scene, object, condition, quality), назначенные моделью одним проходом по контактным листам; чеклист — `docs/photo-review-checklist.md`, автоматического классификатора нет. В собранном `buildings.json` у фотографии появляются `id`, `file` (`photos/<city>/<sha256>.webp`) и `thumb` (`thumbnails/<city>/<sha256>.webp`); `npm run check` сверяет имя полного файла с его SHA-256 и sidecar с бандлом. Сохранять полную достаточную атрибуцию: некоторые старые скрипты обрезают автора до 180 символов, поэтому их результат нужно проверять. Галерейные скрипты обычно допускают CC BY/CC BY-SA, CC0 и public domain; другие проверяют только наличие атрибуции. Ни один фильтр не заменяет проверку условий конкретного файла. См. [правила переиспользования Commons](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia).

Разовая миграция уже собранных фотографий со старых объектовых путей — `npm run photos:migrate` (`scripts/migrate-photo-ids.py`). Она считает SHA-256, раскладывает файлы в `data/photos/<city>/`, пишет sidecars и заменяет объекты в `photos[]` на id, сохраняя порядок. Скрипт идемпотентен.

**Политика для новых карточек:** сначала свободная лицензия. `scripts/fetch-selected-photos.py` читает `data/photo-candidates.json`, проверяет Commons-метаданные и принимает только CC0/PD/CC BY/CC BY-SA; изображение уменьшается до 1920 px по ширине и сохраняется в WebP. Для файлов в общественном достоянии Commons часто не отдаёт `LicenseUrl`; если в `Credit` указано «Own work», скрипт подставляет ссылку на `Template:PD-self`, как в уже опубликованных карточках. Если свободного снимка нет, `scripts/fetch-fallback-photos.py` читает `data/photo-fallbacks.json` и добавляет фото реестра с шириной до 1200 px (обычно меньше, потому что оригиналы реестра маленькие): автор «Реестр памятников Грузии (автор не указан)», лицензия «Не установлена», ссылка на запись реестра и пометка в `modifications`, что полное качество не используется. Кандидатов реестра удобно брать из слоя `CulturePortalService/MapServer/4`: поле `PhotoAddress` отдаёт ссылку на файл, запись сопоставляется с контуром OSM по IoU и адресу, а не только по близости точки. Это временная иллюстрация, а не подтверждение права на публикацию; при первой возможности её нужно заменить свободной. Фото Google Maps/Places в атлас не переносятся: условия сервиса не дают достаточного основания для переиспользования. Полная политика — [photo-policy.md](photo-policy.md).

Батч 1 ноября 2026 года добавил 54 свободных снимка Commons и обновил 126 существующих до 1920 px (там, где исходник позволяет). Цель — три разных фотографии на объект; 19 карточек достигли трёх, 65 — двух, у 315 одна, 4 без фотографии: оранжерея Ботанического сада, дом Анны Мадатовой, баня дочери царя и корпус бывшей Нерсисянской семинарии (Кавказский университет). Для большинства обычных исторических домов в Commons есть только один проверяемый кадр; дубли отбрасывались по perceptual hash, кадры с другим номером дома — по категориям файла. Ручной отбор прошли 76 кадров, из них 54 добавлены после дедупликации.

Ранняя редакционная карточка бывшего министерства автодорог (`bank-georgia`) была исключена из начального набора из-за неразрешённой проверки прав на конкретную фотографию. Само здание сейчас присутствует как `osm-1236448832` с другим, свободным снимком; не возвращать старую карточку или старое фото только потому, что фотолицензия заполнена. Сохранять атрибуцию OSM и [ссылку на условия OSM](https://www.openstreetmap.org/copyright).

Несмотря на русский язык по умолчанию, текущий контракт содержит `ru`, `en`, `ka`, `uk`. Для новой карточки обязательны адресные переводы, описания и записи справочников атрибутов на четырёх языках. Если `histories` присутствует, проверка требует все четыре непустых перевода; если нет — `history` должен быть пустым. Все переводы пишутся прямо в карточку; отдельных translation-файлов больше нет. Изменение только русского текста не считается полным переводом: `assemble-atlas.mjs` требует все четыре языка.

Автоматическая транслитерация/замены в `build-data.py` используются для подписей подложки, а не для карточек; в карточках формы имён уже проверяются редактором. `originalLanguage='ka'` сейчас стоит во всех текущих карточках — это привязка к набору Тбилиси, которую нельзя молча переносить на произвольную страну.

## 8. Батч-определение адреса и Place ID через Google API

### Назначение и правило пяти метров

Скрипт [batch-google-addresses.py](../scripts/batch-google-addresses.py) обрабатывает список координат последовательно. Python 3, только стандартная библиотека. Нужен ключ `GOOGLE_MAPS_API_KEY` в окружении с доступом к **Geocoding API** и **Places API (New)**. `.env` самостоятельно не читается. Ключ не записывается в отчёт и не выводится в диагностике.

Google Geocoding возвращает адресные результаты, включая Place ID; Nearby Search ищет места поблизости. Поэтому адрес дома и достопримечательность определяются двумя запросами, а не попыткой представить обычный дом как театр. См. [обратное геокодирование v3](https://developers.google.com/maps/documentation/geocoding/guides-v3/requests-reverse-geocoding) и [Nearby Search (New)](https://developers.google.com/maps/documentation/places/web-service/nearby-search).

Алгоритм проекта:

1. `GET https://maps.googleapis.com/maps/api/geocode/json`: `latlng`, язык, `result_type=street_address|premise`, `location_type=ROOFTOP`.
2. Повторно проверить результат локально: Place ID, тип `street_address`/`premise`, `ROOFTOP`, компоненты улицы и номера дома. Посчитать расстояние Haversine между входной точкой и `geometry.location`. Выбрать ближайший подходящий результат с расстоянием **не больше 5.0 м**, без предварительного округления.
3. Нет дома в пределах 5 м → `unmatched`, причина `no_house_within_5m`, без запроса достопримечательностей и без расширения радиуса.
4. Есть дом → `POST https://places.googleapis.com/v1/places:searchNearby`, круг радиусом 5 м вокруг входной точки, `rankPreference=DISTANCE`, максимум 20 результатов. FieldMask явно запрашивает ID, имя, координату, типы, адресные компоненты, адрес, ссылку Maps и статус деятельности.
5. Отобрать культурные/исторические и религиозные объекты: например, `performing_arts_theater`, `opera_house`, `museum`, `historical_landmark`, `tourist_attraction`. Полный разрешённый список — `LANDMARK_TYPES` в скрипте. Магазин или ресторан не становится достопримечательностью из-за наличия общего типа `point_of_interest`.
6. Для достопримечательности требуются те же улица и номер дома, что у найденного адреса, и её собственная точка не дальше 5 м от входной. Сравнение адреса нормализует регистр, пробелы и пунктуацию, но не угадывает эквивалентность разных написаний. Закрытые временно/постоянно места исключаются. При необходимости вход задаёт более узкие `landmarkTypes` и `landmarkName`.
7. Выбрать ближайшую подходящую достопримечательность. Если две ближайшие отличаются по расстоянию не более чем на 0.5 м, считать выбор неоднозначным и оставить дом. Если подходящей достопримечательности нет — также оставить дом.

Порог относится **к расстоянию между точками**, а не к границе OSM-полигона. Для большого здания Google может ставить адресную точку дальше 5 м от его центра — тогда автоматической привязки не будет. Увеличивать допуск ради покрытия нельзя. Без контура алгоритм не доказывает, что близкая точка принадлежит именно этому зданию; совпадение адреса уменьшает риск, редакционная проверка остаётся нужна.

Nearby Search ограничен 20 результатами: в насыщенном месте нужная карточка может не попасть в ответ. Достопримечательность с другим написанием адреса или точкой у входа дальше 5 м тоже не будет выбрана. Это допустимые пропуски, а не основание привязать соседнее заведение. `landmarkName` проверяет наличие всех нормализованных слов в Google-имени, без перевода и нечёткого сравнения.

### Вход и запуск

Вход — непустой JSON-массив с уникальными строковыми `id` и координатами `[долгота, широта]`. Можно подать записи из `data/atlas/tbilisi/*.json` или собранного `buildings.json`: скрипт использует `coordinates`, а дополнительные поля сохраняет в отчёте. Для компактного отчёта лучше выделить только необходимые поля. Синтетический пример формата, не проверенная привязка:

```json
[
  {
    "id": "example-theatre",
    "coordinates": [44.796167, 41.701306],
    "landmarkTypes": ["performing_arts_theater", "opera_house"]
  },
  {"id": "example-house", "coordinates": [44.8, 41.7]}
]
```

После передачи ключа в окружение:

```sh
python3 scripts/batch-google-addresses.py /tmp/atlas-address-input.json --output /tmp/atlas-address-report.json
python3 scripts/batch-google-addresses.py /tmp/atlas-address-input.json --output /tmp/atlas-address-report.json --resume
```

`--language ru` по умолчанию; `--interval 0.2` — минимальная пауза между запросами, `--timeout 30` — timeout HTTP. На объект приходится один запрос Geocoding и, если дом найден, один Places; временные ошибки могут привести к трём попыткам каждого запроса. Скрипт не запускает параллельные запросы и не запрашивает фотографии, отзывы или контактные данные.

Отчёт сохраняется атомарно после каждой записи. Существующий выходной файл без `--resume` не перезаписывается. При продолжении сверяются входные записи и параметры; успешные и `unmatched` пропускаются, ошибки повторяются. Чтобы повторно проверить прежний `unmatched`, использовать новый файл отчёта. После прерывания уже завершённые записи сохраняются. Запуск печатает прогресс `[N/M]` с ETA по фактической скорости; при `--resume` отдельно сообщает, сколько записей уже готово и сколько осталось обработать.

### Выход и перенос в атлас

Корень отчёта содержит `version`, подпись входа `signature`, `language`, `maxDistanceMeters`, `results`. Для записи:

- `status`: `matched`, `unmatched` или `error`; `reason` объясняет решение; `checkedAt` — время проверки UTC.
- `house`: найденный дом с `placeId`, адресом, точкой, расстоянием и нормализованным ключом адреса либо `null`.
- `selected`: выбранная достопримечательность (`kind=landmark`) или дом (`kind=house`) с `placeId`, `sourceUrl`, адресом, именем, типами, координатами и расстоянием; при отсутствии результата/ошибке — `null`.

Ошибки сети, HTTP, отказ доступа, квота и статус API не считаются отсутствием адреса. Если поиск достопримечательности упал после успешного поиска дома, дом остаётся в отчёте, но `selected=null`, `status=error`; повторить через `--resume`. Код выхода 1 означает наличие ошибок обработки, 0 — завершение без них, включая честные `unmatched`.

Скрипт **не меняет** `data/`, `public/` и существующие Place ID. Перед переносом просмотреть `matched`, сопоставить идентичность здания, проверить повторяющиеся Place ID у разных контуров. Один адрес может обслуживать несколько корпусов; дубликаты требуют решения редактора. Затем внести проверенные `placeId` и `googlePlaceIdSource` в `data/atlas/tbilisi/<id>.json`, не меняя остальные поля карточки. Не менять текущий редакционный адрес автоматически по полю `selected.address`: адреса в Google и локальные переводы — разные источники, их нужно согласовать.

Подробный отчёт нужен для исследования; его хранение/публикацию и допустимое использование полей Google проверять по актуальным условиям сервиса. Не помещать ключ или полный HTTP URL с ключом в репозиторий. В публичной карточке сейчас используется Place ID для ссылки на Google Maps; внешняя ссылка открывается по действию пользователя.

В [правилах Geocoding API](https://developers.google.com/maps/documentation/geocoding/policies) и [Places API (New)](https://developers.google.com/maps/documentation/places/web-service/policies) Place ID отдельно исключён из ограничений на кеширование. Для исследовательской очереди сохранять идентификаторы и статусы отдельно от полного временного ответа Google; перед отображением других данных Google соблюдать соответствующие требования и условия аккаунта.

Раньше Place ID лежали отдельным `data/google-place-ids.json`; теперь они перенесены в поля `googlePlaceId` и `googlePlaceIdSource` соответствующих карточек. В старых значениях `sourceUrl` встречаются Google Maps и Waze. Это сохранённые подтверждающие ссылки, **не свидетельство того, что Waze был источником выгрузки**: по уточнению владельца Place ID получали из Google API. Старый загрузчик не сохранён; новый скрипт документирует воспроизводимый процесс следующих запусков. Правила ручной проверки и способ получить актуальный список — [ручная проверка Place ID](google-place-id-manual-review.md).

Тестирование без внешних запросов:

```sh
python3 -B -m unittest discover -s tests -p 'test_google_addresses.py'
```

Это отдельные Python-тесты; `npm test` запускает только JS-тесты. Тесты проверяют дистанцию, качество адреса, выбор и неоднозначность достопримечательности, ошибки и продолжение обработки; доступность API и реальные привязки ими не подтверждаются.

## 9. Пошаговый процесс добавления нового города

1. **Проверить рабочее дерево.** Прочитать `AGENTS.md`, этот документ, код затрагиваемых сборщиков. Сохранить пользовательские правки. Определить город, границу, архитектурные критерии и объём пилота по качеству, без квоты в 90/100 зданий.
2. **Изолировать исходники новой локации.** До универсального загрузчика хранить новые исследования отдельно, например `raw/<city>/`, `data/atlas/<city>/`; `scripts/assemble-atlas.mjs` уже принимает `--city` и `--out`, но приложение пока читает только Тбилиси. Не класть XML другого города под общий `osm-grid-*`: glob смешает наборы. Зафиксировать план подключения.
3. **Составить список кандидатов.** OSM + местные реестры, учреждения и профильные источники; записать причину включения и исключения. Сверить бывшие/нынешние названия, корпуса и дублеты. Найти важные здания, отсутствующие в OSM-фильтрах.
4. **Получить контуры и подложку.** OSM через тематические Overpass-запросы, полная геометрия отобранных зданий; только разрешённые категории фона. Сохранить запросы и ответы. Кандидаты без достоверного контура пока не публикуются.
5. **Заполнить факты.** Разнести даты постройки/открытия/перестройки, авторство и стиль; сохранить прямые источники и неопределённость. Не заменять неизвестное предположением.
6. **Проверить адреса.** Сначала собрать адресные сведения из источников; запустить батч Google на входных координатах, проверить отчёт и сопоставления. Отсутствие Place ID не блокирует историческую карточку; ссылка может работать по координате.
7. **Собрать медиа.** Найти, визуально проверить, атрибутировать и преобразовать доступные фотографии. Несколько ракурсов желательно, но не любой ценой. Непроверенные снимки оставить за пределами публикуемой галереи.
8. **Подготовить переводы и справочники.** Все обязательные языки, стабильные ID архитекторов/стилей/районов/подписей дат; не плодить варианты одного автора. Справочники города лежат в `aux/<city>/`; `npm run aux:merge` собирает их в `data/aux/<city>.json`, после чего `assemble-atlas.mjs` подставит производные поля из `names`/`addresses` и aux.
9. **Подключить город в код.** `assemble-atlas.mjs` уже принимает `--city` и `--out`, но приложение пока читает только Тбилиси; нужно выделить загрузку/пакеты по городам и адаптировать проверки. Сохранить работу Тбилиси и честное пустое состояние городов без набора. Подготовка JSON сама по себе не включает город в UI.
10. **Собрать и проверить.** Сравнить diff исходных и сгенерированных данных, проверить геометрию, манифест и браузер. Передать отчёт о покрытии, происхождении, пробелах и реально выполненных проверках.

### Что в коде привязано к Тбилиси

- `fetch-osm.py`: сетка; `build-data.py`: имя городской выборки и грузинские fallback-формы подложки; `assemble-atlas.mjs`: по умолчанию каталог `data/atlas/tbilisi` и выходной `public/atlas/buildings.json`; `resolve-geometries.py`: ID отношений и Метехи.
- `research-heritage.py`: прежние фильтры кандидатов и пути; `data/atlas/tbilisi/<id>.json`: ручная запись карточек и обязательные переводы.
- Фотозагрузчики: названия статей, категории, файлы, ручные ID; не универсальные команды для нового города.
- `scripts/check-data.mjs`: допустимые координаты жёстко ограничены долготой 44.6–45 и широтой 41.5–41.9. Для других городов нужна проверка по соответствующим границам, а не удаление пространственной проверки.
- `src/App.tsx`: загрузка одного `atlas/manifest.json`, отсутствие `cityId` в `Building`, ветка UI только для `tbilisi`, надписи города, `Tbilisi, Georgia` в Google-ссылке.
- `src/MapView.tsx`: начальный центр `[41.715,44.800]`, обзор/сброс карты и геолокационные границы нужно сверить при подключении. Часть охвата уже вычисляется по контурам; это не полноценная поддержка разных городов.

## 10. Пересборка, проверки и обновление

Обычная локальная пересборка текущего набора не требует повторного обращения к внешним источникам:

```sh
npm run layers:build                 # подложка и контуры; сборка только при изменении входов
npm run layers:force                 # то же с принудительной пересборкой
python3 scripts/validate_cards.py    # исходные карточки и собранный JSON
npm run assemble                     # только упаковка карточек в buildings.json
npm run check                        # слои + упаковка + TypeScript + проверка данных
npm test
npm run build                        # слои + упаковка + манифест + dist/
npm run verify
```

Зависимости приложения устанавливаются `npm ci`, если ещё не установлены. Для исследовательских фотоскриптов нужен Pillow; для `validate_cards.py`, `resolve-geometries.py` и `extract-tbilisi-building-outlines.py` — Shapely/PyOsmium. Часть скриптов ищет его в `.deps`; общего lockfile Python-зависимостей нет. Запускать из корня репозитория. Не выполнять все `fetch-*.py` подряд.

Все длительные загрузчики, сборщики и проверки печатают прогресс в stderr: сколько выполнено из общего числа, процент, прошедшее время, оценку остатка и скорость. Итоговые данные и отчёты остаются в stdout, поэтому перенаправление вывода не ломается. При `--resume` или кэше прогресс показывает, сколько записей уже готово и сколько реально осталось; при неизвестном общем числе ETA не выдумывается. Правила, готовые helper'ы `scripts/progress.py` и `scripts/lib/progress.mjs`, примеры и чек-лист — [long-running-scripts.md](long-running-scripts.md). Новый долгий скрипт без прогресса не принимается.

`build-data.py` формирует только подложку и контуры зданий из сохранённых OSM-источников; карточки он не создаёт. `npm run build` и `npm run check` запускают его через `scripts/build-map-layers.mjs`, который хеширует `raw/osm-grid-*.xml`, `raw/osm-tbilisi-selected.json`, `raw/osm-tbilisi-building-outlines.geojson`, редакционные переводы и сам `build-data.py`. При совпадении хеша и наличии обоих файлов шаг пропускается (около 0,2 с вместо 5 с), иначе слои пересобираются; `npm run layers:force` пересобирает принудительно. Отметка хранится в `.cache/map-layers.json` (игнорируется Git). Если Python 3 нет, а готовые `public/atlas/*.geojson` уже лежат, сборка использует их с предупреждением. Дальше `npm run build` запускает `assemble-atlas.mjs`, создаёт манифест, проверяет TypeScript и формирует `dist/`. Отдельные `enrich-basemap-*.mjs` исторически правили уже сгенерированный GeoJSON; их функции перенесены в Python-сборщик, поэтому не считать их обязательными постшагами без проверки необходимости.

`npm run check` сначала собирает `data/aux/tbilisi.json`, создаёт недостающие превью в `data/thumbnails/`, синхронизирует `data/photos/` и `data/thumbnails/` с публикуемыми зеркалами и пересобирает общий JSON из `data/atlas/tbilisi/`, затем проверяет поля, переводы, уникальность ID, диапазон координат, интервалы лет, наличие Polygon/MultiPolygon, пути и сигнатуру WebP полного файла и превью в исходнике и опубликованном файле. Для каждой фотографии он также сверяет SHA-256 полного файла с его именем, `width`/`height` с реальными размерами WebP и метаданные sidecar с собранным бандлом. Отдельно `npm run aux:merge` только пересобирает городской aux. `npm test` проверяет доменную фильтрацию и связанные сценарии из `tests/*.test.mjs`. `npm run verify` проверяет уже собранный `dist`: ресурсы манифеста, размеры и SHA-256, наличие контуров и отсутствие внешних ассетов в HTML. Эти проверки не устанавливают историческую достоверность, права или совпадение снимка с объектом.

Проверки на 1 ноября 2026 года: `npm run check` (403 здания), `npm test` (21/21), `python3 -m unittest tests/test_google_addresses.py` (15/15) и `python3 scripts/validate_cards.py` (0 ошибок, только предупреждения по старым пустым переводам) проходят. Браузерная E2E-проверка не выполнялась; запросов к Google API при подготовке этого снимка не было.

Манифест включает `buildings.json`, `basemap.geojson` и уникальные файлы фотографий, на которые ссылаются карточки: полные изображения и их превью из `thumbnails/`. Фотографии, просто лежащие в папке, автоматически не становятся галереей. Начальная загрузка содержит только данные карты; фотографии скачиваются по требованию через `src/photos.ts` с проверкой размера и SHA-256: сначала все превью объекта, затем полные файлы галереи. Манифест по-прежнему перечисляет все фото, поэтому его размер растёт вместе с набором, но байты изображений не входят в первую загрузку. Каталог запрашивает превью только видимых карточек, а выбор объекта — все фото этого объекта.

При проверке в браузере использовать HTTP на localhost или HTTPS. Открыть карту/каталог, фильтры и неизвестные значения, все галереи и источники, переключение городов, мобильный инспектор, клавиатуру; проверить подложку вне скопления зданий, сетевые запросы после загрузки и состояния геолокации. Внешние карты/тайлы не должны запрашиваться при просмотре. Отдельно отличать работу уже загруженной страницы без сети от повторного автономного запуска: PWA не реализована.

При обновлении фиксировать изменения: новые/удалённые объекты, смена геометрии или Place ID, потерянные фотографии, заполненные/потерянные даты, размер пакета, спорные решения. Изменившийся файл по старому имени нельзя без проверки считать той же фотографией; кэш фотоскриптов часто проверяет только существование и размер. Сохранять стабильные ID и ручные исправления, делать сборку из исходников, проверять diff перед публикацией. Codex не запускает `make`, `docker` и не делает push без прямого запроса.

## 12. Пайплайн очереди: сбор, отчёт, проверка

Для массового разбора очереди добавлены три скрипта. Они не меняют `data/` и `public/`, работают с локальным кэшем и не заменяют редакционное решение.

```sh
# детерминированный сбор фактов по кандидатам (реестр, OSM, геометрия, Place ID, Commons, пересечения)
python3 scripts/queue_collect.py --only 28,49 --out work/queue
python3 scripts/queue_collect.py --delay 0.3

# сводка по очереди; по умолчанию в stdout, файл — только с --out
python3 scripts/queue_report.py --out work/queue/report.md

# проверка исходных карточек, переводов и полигонов перед сборкой
python3 scripts/validate_cards.py
```

Артефакты лежат в `work/queue/` (`<n>/collect.json`, `index.jsonl`, `cache/`) и исключены из git. HTTP-ответы кэшируются; `--refresh` игнорирует кэш. Коллектор последовательный, с паузой и повторами на 429: не запускать его в несколько параллельных процессов по одним и тем же way. Он печатает прогресс `[N/M]` с ETA по фактической скорости и отдельно отмечает кэшированные и ошибочные карточки; `validate_cards.py` показывает прогресс по карточкам, зданиям и проверке пересечений.

Если очередь ссылается на соседний OSM way, а объект описан relation, исправление задаётся в `data/osm-candidate-overrides.json` (номер кандидата → `type`, `id`, причина). Коллектор соберёт relation из внешних контуров и сохранит `geometryFlags`; пример — баня №5, где way и relation вообще не пересекаются. Не подменяйте override «на глаз»: это редакционное решение с причиной.

`queue_collect.py` только собирает факты и не решает, добавлять ли объект. `queue_report.py` показывает, что уже собрано и где ошибки; если рядом с `collect.json` появится `verdict.json`, отчёт подхватит вердикт. `validate_cards.py` проверяет обязательные поля, ключи стилей/дат/районов, переводы, WebP-файлы, валидность полигонов и пересечения; предупреждения о пустых переводах допустимы для неизвестных адресов, ошибки — нет.

Полная схема этапов и правила разведения параллельных процессов — в [research-pipeline.md](research-pipeline.md). Скрипты закрывают только `collect`, `report` и `validate`; `enrich`, `adjudicate` и `edit` остаются агентскими этапами с JSON-артефактами.
