# Политика фотографий

Правило проекта: **лучше какая-то фотография, чем никакой**, но права, атрибуция и достоверность не подменяются количеством. Целевой минимум — **три фотографии на объект**, когда для них есть проверяемые снимки; если надёжных кандидатов меньше, честный пробел лучше подстановки соседнего здания.

## Приоритет

1. **Свободная лицензия**: CC0, public domain, CC BY, CC BY-SA.
2. **Фото реестра памятников** — только если свободного снимка нет.
3. **Без фото** — если нет ни свободного, ни реестрового снимка.

Фотографии Google Maps/Places не переносятся: условия сервиса не дают достаточного основания для переиспользования в атласе. Google можно использовать для проверки места, но не как источник изображения.

## Сколько фотографий

- Цель — **три** разных снимка одного объекта; в галерее допускается до четырёх. Больше — только если это действительно разные ракурсы, а не дубли.
- Сначала заполняются карточки с одной фотографией или без неё. Если для объекта нашлось меньше трёх надёжных снимков, галерея остаётся короче; добивать её чужим корпусом, интерьером, мемориальной доской или общей панорамой улицы запрещено.
- **Дубли одного кадра не считаются ракурсами.** Точные копии, одна и та же фотография в разных размерах и почти совпадающие кадры (perceptual hash) отбрасываются; остаётся версия с лучшим разрешением и более свободной лицензией.
- Предпочтение — фасаду и общему виду здания. **Кадры с несколькими объектами** (соседний корпус, ряд домов, панорама площади) допустимы только как последний выбор и не должны быть первыми в галерее.
- Отбрасываются планы, карты, гербы, марки, портреты, таблички, интерьеры, лестницы, двери и фрагменты декора: это не фотография объекта в атласе.
- Название файла на Commons — только гипотеза. Адрес в названии проверяется по категориям файла: если категория называет **другой номер дома на той же улице**, снимок отклоняется. Совпадение категории с адресом или названием здания повышает приоритет.

## Разрешение и формат

- **Свободная лицензия** (Commons: CC0/PD/CC BY/CC BY-SA): ширина — **до 1920 px**.
- **Неизвестная или коммерческая лицензия** (в том числе фото реестра): ширина — **до 1200 px**.
- **Commons отдаёт только стандартные миниатюры.** Прямые ссылки на оригиналы и произвольные ширины миниатюр отклоняются (HTTP 429/400). Допустимые шаги — 20, 40, 60, 120, 250, 330, 500, 960, 1280, 1920, 3840 px; для восстановления берётся наибольший стандартный размер, не превышающий ширину оригинала. Поэтому файл может остаться меньше исходника (например, 1280 px при оригинале 1872 px) — это ограничение Wikimedia, а не апскейл.
- Уменьшение выполняется только по ширине, с сохранением пропорций. Оригинал **никогда не растягивается**: если источник меньше лимита, файл остаётся исходного размера.
- Полный файл — RGB WebP, quality 80–82; превью для карточки — WebP шириной **до 720 px**, quality 75, с сохранением пропорций и без апскейла. 720 px достаточно для инспектора шириной 390 px на экране с двойной плотностью и для карточек каталога, но заметно легче полного файла.
- В `modifications` честно указывается фактическая ширина после уменьшения и преобразование в WebP; полное качество не выдаётся за оригинал.
- В sidecar `width` и `height` — фактические пиксельные размеры **сохранённого WebP**, а не upstream-оригинала. Их синхронизирует `scripts/sync-photo-dimensions.py` (`npm run photos:dimensions`); при замене изображения файл и sidecar получают новый sha256, а размеры пересчитываются. `assemble-atlas.mjs` переносит их в `buildings.json`, `check-data.mjs` и `validate_cards.py` сверяют их с реальными размерами файла.
- Полный файл: `data/photos/<city>/<sha256>.webp`; метаданные: `data/photos/<city>/<sha256>.metadata.json`; превью: `data/thumbnails/<city>/<sha256>.webp`. SHA-256 считается по точным байтам WebP. `data/thumbnails/` генерируется и не хранится в Git; `public/atlas/photos/` и `public/atlas/thumbnails/` — сгенерированные зеркала, их создаёт `scripts/sync-photos.mjs`.
- В исходной карточке `photos` — только упорядоченный массив sha256-идентификаторов; это канонический порядок хранения. Основной режим сортирует галерею по `rating` (см. ниже), а не по порядку массива. `file`, `thumb` и поля метаданных подставляет `scripts/assemble-atlas.mjs` из sidecar-файлов. Отдельного `photos.json` нет: канонический словарь — это sidecars, поэтому нет второго источника истины.
- Имя файла — это его содержимое: если изображение изменилось, получается новый id и старый кэш не переиспользуется. Одинаковые байты в разных объектах делят один файл и один sidecar; конфликтующая атрибуция для одного и того же изображения — ошибка. Превью пересоздаётся только когда файл-источник новее, поэтому повторная сборка не запускает конверсию зря.

## Теги источника

- `sourceTags` — необязательный массив строк, которые источник даёт сам. Для Commons это категории файла без префикса `Category:`, отсортированные и без дублей. Они сохраняются дословно и поэтому могут включать служебные категории (лицензии, загрузки, координаты, авторы); это сырой слой, а не редакционная классификация.
- `scripts/sync-photo-source-tags.py` (`npm run photos:source-tags`) сначала использует кэш `work/photo-research/candidates.json`, недостающие категории запрашивает через Commons API и кэширует в `work/photo-research/source-tags-cache.json`. Для фото реестра тегов нет, поле отсутствует.
- `apply-photo-candidates.py` записывает `sourceTags` для новых снимков из уже собранного `categories` кандидата, поэтому теги появляются вместе с загрузкой исходника, а не отдельной ручной операцией.

## Визуальные теги

- `visualTags` — необязательный массив стандартизованных оптических тегов. Таксономия — `data/photo-visual-tags.json`: **43 тега**, меньше лимита в 50. Четыре группы:
  - `scene`: `facade`, `interior`, `street`, `courtyard`, `multiple-buildings`, `panorama`, `aerial`;
  - `object`: `balcony`, `window`, `door`, `roof`, `dome`, `tower`, `arch`, `column`, `staircase`, `fence-wall`, `detail`, `plaque`, `people`, `car`, `tree`, `sky`, `water`, `construction`, `scaffolding`, `ruin`, `graffiti`, `shopfront`, `air-conditioner`, `street-lamp`, `sign`;
  - `condition`: `nighttime`, `snow`, `rain`;
  - `quality`: `foreground-distraction`, `subject-far`, `occluded`, `cluttered`, `tilted`, `blurry`, `dark`, `low-resolution`.
- **Разметку выполняет модель одним проходом, а не скрипт-классификатор.** CLIP-конвейер удалён после проверки: на 30 случайных фото precision 0.825, recall 0.322, точных совпадений набора 0/30.
- Один проход: модель читает контактный лист один раз, сначала назначает content-теги всем шести кадрам, затем по тем же кадрам — quality-теги. Это не два отдельных чтения изображения. Полный чеклист — [photo-review-checklist.md](photo-review-checklist.md).
- Процесс:
  1. `npm run photos:review-sheets -- --size 6` — листы и `work/photo-research/review/index.json`;
  2. модель читает листы один раз и выбирает content- и quality-теги, не подглядывая в старую разметку;
  3. теги складываются в JSON-батч и применяются `npm run photos:apply-tags -- --file work/photo-research/review/batch-001.json`;
  4. `npm run photos:review-status` показывает покрытие.
- Служебный `scripts/photo-visual-review.py` **не классифицирует**: он только нарезает листы, проверяет таксономию и записывает уже принятые моделью теги. Никаких ONNX/CLIP-зависимостей в проекте нет.
- 6 фото на лист — компромисс между ценой и детализацией. 9–12 фото на лист дешевле, но балконы, окна, люди и таблички на мелких ячейках теряются.
- Quality-теги не отменяют content-теги: кадр может быть `facade` и одновременно `tilted` или `subject-far`. Они не влияют на права, атрибуцию или обязательный отбор; это слой для поиска, сортировки и выборочной проверки.
- Пайплайн: `collect-photo-candidates.py` → `apply-photo-candidates.py` → `npm run photos:source-tags` → `npm run photos:review-sheets` → модель (один проход) → `npm run photos:apply-tags` → `npm run photos:rate` → `npm run photos:thumbs`.

## Рейтинг фотографии

`rating` — целое число **0–100**, детерминированная оценка пригодности снимка для атласа. Это не оценка художественной ценности и не замена атрибуции. **100** — максимально чистый профессиональный кадр фасада: высокое разрешение, горизонтальная композиция, дневной свет, хороший контраст, без quality-флагов и визуального мусора.

Скрипт — `scripts/rate-photos.py` (`npm run photos:rate`), без модели и без сети. Он читает `width`, `height`, `visualTags` и считает по сохранённому WebP среднюю яркость, контраст и квантили p10/p50/p90. Повторный запуск идемпотентен: sidecar перезаписывается только при изменении рейтинга. `npm run build` пересчитывает рейтинг, `npm run check` проверяет его актуальность.

База — 100 баллов:

| Компонент | Максимум | Правило |
|---|---:|---|
| Разрешение | 30 | 1920+ px и ≥2 Мп — 30; 1280+ и ≥1 Мп — 26; 960+ — 22; 800+ — 16; 640+ — 8; меньше — 0 |
| Фасад | 35 | `facade` — 26, уличный/дворовый контекст — +4, архитектурная деталь — +5; `interior` ограничен 6, `detail` — 10, `panorama`/`aerial` — 12; `multiple-buildings` −6, `construction`/`scaffolding` −5, `ruin` −2 |
| Свет | 25 | средняя яркость и p90 в целевой зоне; низкий контраст штрафуется; для `nighttime` — не выше 12, при тёмном кадре — 6/0; для `dark` — не выше 4 |
| Кадрирование | 10 | горизонталь 1.2–1.8 — 10; 1.0–1.2 или 1.8–2.2 — 7; портрет/экстремальная панорама — 4/2 |

База умножается на коэффициент качества:

`qualityFactor = max(0.15, 1 − сумма штрафов)`

Штрафы: `blurry`/`dark` — 0.35; `low-resolution` — 0.45 (также выводится из `width < 800`, даже если тег забыт); `subject-far` — 0.22; `tilted`/`foreground-distraction`/`occluded`/`cluttered` — 0.18; `nighttime` — 0.08; `construction`/`scaffolding` — 0.10; `multiple-buildings` — 0.08; `car`/`people` — 0.03; `tree`/`street-lamp`/`sign`/`fence-wall` — 0.02.

После умножения действуют потолки видимости: `dark` — 25; средняя яркость <25 или p90 <40 — 15; <35 или p90 <55 — 30; `nighttime` при средней яркости <50 — 45; `nighttime` при p90 <70 — 40. Итог: `min(100, round(base × qualityFactor), cap)`.

Рейтинг используется в основном режиме: галерея сортируется по убыванию `rating` (при равенстве — исходный порядок). Если у объекта есть **три снимка с рейтингом >50**, снимки с рейтингом **<50** скрываются; ровно 50 остаётся. Если сильных снимков меньше трёх, показываются все, включая слабые. Карточка каталога берёт первый снимок после этой сортировки.

## Атрибуция

- Каждый sidecar `<sha256>.metadata.json` обязан содержать `author`, `license`, `licenseUrl`, `source`, `modifications`, `width`, `height`, `rating`; `description` — по желанию. В собранном `buildings.json` у фотографии появляются ещё `id`, `file` и `thumb`.
- `source` — страница файла на Commons (или запись реестра), а не прямой URL картинки; `licenseUrl` — страница версии лицензии. Для неизвестной лицензии — ссылка на исходную запись.
- Автор и лицензия берутся со страницы файла, а не угадываются. Если автор указан ссылкой или HTML-разметкой, сохраняется читаемое имя.
- Атрибуция видна в интерфейсе: в инспекторе — блок «Данные и фотография» для текущего снимка, в полноэкранной галерее — подпись под кадром со ссылками на источник и условия лицензии. При перелистывании подпись меняется вместе с фотографией.
- Для фото реестра: автор «Реестр памятников Грузии (автор не указан)», лицензия «Не установлена», `licenseUrl` — запись реестра, `source` — URL файла, в интерфейсе ссылка подписана **«Источник фото»**, а не «Условия лицензии».
- Права фотографа и права на изображённое архитектурное произведение проверяются отдельно. Свободная лицензия снимка не отменяет вторую проверку.

## Как искать фотографии

Основной конвейер:

1. `scripts/collect-photo-candidates.py` — собирает кандидатов, ничего не записывая в карточки:
   - `P180` («изображает») и `P18` из Wikidata для объектов с QID;
   - тег `wikimedia_commons` из OSM (файл или категория);
   - файлы Commons, найденные по улице и номеру дома (в том числе грузинские названия вида «ლადო ასათიანის 38»);
   - файлы, найденные по выразительному названию объекта;
   - геопоиск вокруг контура как последний вариант — только при совпадении названия или адреса;
   - категории файла для подтверждения или отклонения адреса.
   Поиск идёт через HTML-страницу Special:Search и кэшируется в `work/photo-research/`, метаданные — пакетами через Commons API. Кандидаты и отчёт складываются в `work/photo-research/candidates.json`; в карточки скрипт не пишет.
2. `scripts/apply-photo-candidates.py` — скачивает выбранные снимки, применяет лимиты 1920/1200, убирает почти-дубли по perceptual hash, добивает галерею до трёх, ставит свободные снимки перед fallback реестра, сохраняет файлы по SHA-256 и пишет порядок id в карточки. Список ручного отбора после визуальной проверки — `data/photo-gallery-selection.json`; кандидаты вне его не добавляются. Отчёт — `work/photo-research/applied.json`.
3. `npm run photos:thumbs` — создаёт недостающие превью 720 px в `data/thumbnails/` по sha256-идентификаторам; `npm run build`, `npm run check` и `npm run dev` вызывают этот шаг автоматически. После разовой миграции старых данных `npm run photos:migrate` раскладывает файлы по sha256 и sidecars.

Проверка перед добавлением:

- снимок показывает именно этот объект, а не соседний корпус;
- в названии и категориях нет другого номера дома на той же улице;
- лицензия и автор взяты со страницы файла;
- для свободной лицензии сохранена ссылка на её версию;
- для fallback явно стоит «Не установлена» и ссылка на источник;
- изображение уменьшено, не выдаётся за оригинал;
- кадр не является планом, интерьером, табличкой или общей панорамой.

## Fallback: фото реестра

- Основной путь — `scripts/fetch-registry-photos.py`:
  - `--review` запрашивает публичный API записи `api/Immovable/GetImmovableObject?id=<registryId>` и читает полный массив `photoIds`, а не только `PhotoAddress`. Для каждого файла сохраняются размеры, SHA-256 и perceptual hash; контактные листы по 6 кадров и `index.json` складываются в `work/registry-photos/<card-id>/review/`. В карточки на этом шаге ничего не пишется.
  - `--apply` берёт ручной отбор из `data/registry-photo-selection.json`, использует уже скачанный кэш, применяет лимит 1200 px, пишет sidecars и заменяет старые фото той же записи. Отчёт — `work/registry-photos/applied.json`.
- `PhotoAddress` — обычно первый и самый маленький файл. В записи часто лежит тот же кадр в большем размере (например, 327×208 и 640×425) и несколько других ракурсов. Точные дубли отбрасываются по SHA-256, почти-дубли отмечаются по perceptual hash; после визуальной проверки маленькая версия заменяется самой крупной, а не добавляется рядом. Старые фото той же записи удаляются из карточки, чтобы не оставлять дубль; файлы, на которые больше никто не ссылается, удаляются.
- Цель — три разных общих вида, максимум четыре. Детали, окна крупным планом, ограды, интерьеры и кадры соседних корпусов не добивают галерею. Если у записи меньше трёх пригодных кадров, галерея остаётся короче; `--allow-fewer` фиксирует честный пробел.
- Отбор хранится в `data/registry-photo-selection.json`: `registryId`, список `photos` с `id` из `photoIds` и необязательными `visualTags`, назначенными при том же просмотре контактных листов. Пример:
  ```json
  "osm-1207173721": {
    "registryId": 3359,
    "photos": [{"id": 309073, "visualTags": ["facade", "street", "window"]}]
  }
  ```
- Разрешение — до 1200 px по ширине, без апскейла; оригиналы реестра часто 640 px и меньше, поэтому файл остаётся как есть. Улучшение разрешения не выдаётся за полноразмерный оригинал.
- `data/photo-fallbacks.json` и `scripts/fetch-fallback-photos.py` остаются для точечного одиночного fallback, когда у записи нет пригодной галереи; для записей с несколькими фото используйте новый путь.
- Где искать запись: официальный слой [границ и карточек реестра](https://memkvidreoba.gov.ge/arcgisch/rest/services/Culture/CulturePortalService/MapServer/4) отдаёт `ImmovableObjectID`, `Address` и `PhotoAddress`. Запись сопоставляется с контуром OSM по IoU полигонов и адресу; близость сама по себе не доказывает, что на снимке нужный корпус.
- Fallback — временная иллюстрация, а не подтверждение права на публикацию. При появлении свободного снимка он заменяется; по запросу правообладателя удаляется.
