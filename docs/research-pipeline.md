# Как ускорить разбор очереди: замеры и схема конвейера

Срез: 1 ноября 2026 года. Это разбор процесса, а не новые исследования. Основа — две волны по 8 кандидатов, разобранные параллельно четырьмя агентами.

## Где реально уходит время

По журналу волн:

| Волна | Кандидатов | Время агентов | Внешнее время | Среднее на кандидата |
|---|---:|---:|---:|---:|
| 1 (39, 41, 48, 59, 113, 175, 183, 184) | 8 | ~29 мин | ~9 мин | ~3,6 мин |
| 2 (15, 19, 28, 32, 49, 50, 53, 79) | 8 | ~73 мин | ~20 мин | ~9,1 мин |
| Объект 1 (2676) отдельно | 1 | ~5 мин | ~5 мин | ~5 мин |

Разброс внутри волны 2 большой: 15/19 — 10 минут, 53/79 — 15, 49/50 — 20, 28/32 — 28. Это не случайность: чем больше в объекте неоднозначности (адрес, корпус, дата, несколько источников), тем дольше агент копает.

Если грубо разложить время на один «полный» цикл кандидата:

| Работа | Доля | Что именно съедает время |
|---|---:|---|
| Поиск и чтение источников | 40–50% | Профильные сайты, PDF-перечни, Wayback, страницы церквей/музеев, проверка адреса и даты |
| Разрешение неоднозначности | 15–20% | Реестровый полигон ≠ контур здания; адреса 69/65, 138/138а, 148/148а/148б; несколько корпусов на одном участке |
| Фотографии и права | ~10% | Commons, геопривязка, лицензия снимка, отдельно — права на архитектуру |
| Сборка карточки | 15–20% | 4 языка × имя/адрес/описание/история, JSON, переводы, пересборка |
| Координация и отчётность | 10–15% | Ожидание агентов, «дожми», чтение отчётов, сверка цифр, регистр, README |

Главный вывод: **больше всего времени уходит не на геометрию, а на поиск источников и разрешение неоднозначностей**. Геометрия при наличии скрипта считается за секунды; ручная работа — в том, чтобы понять, тот ли это корпус и та ли это дата.

## Почему текущая схема мешает сама себе

1. **Каждый агент — универсал.** Он сам тянет реестр, OSM, геометрию, ищет источники, проверяет фото и пишет вывод. Один и тот же реестр/OSM запрашивается по восемь раз; при параллельном запуске ловим 429 от OSM.
2. **Разные форматы на выходе.** Один агент пишет «HOLD, потому что…», другой — таблицу, третий — карточку. Сводить приходится вручную.
3. **Анализ начинается до того, как собраны факты.** Агент уже строит вердикт, потом находит источник, который его переворачивает (пример 48: сначала «ready», потом выяснилось, что контур — участок с двором).
4. **Общие файлы.** Если бы агенты писали в `data/` или `docs/`, они бы затирали друг друга. Поэтому им запрещено редактировать репозиторий — но тогда весь merge на одном узле.
5. **Нет стоп-правил.** 28/32 занял 28 минут не потому, что объект сложнее, а потому что не было лимита «три запроса — и фиксируем пробел».
6. **Счётчики в README.** Каждое добавление требует синхронизировать число в трёх местах; это чистые потери и источник расхождений.

## Конвейер

Идея: **факты, источники, суждение и текст — разные артефакты**. Каждый этап читает предыдущий JSON и пишет свой; человек/интегратор трогает только финальный merge.

```
queue.jsonl
   │
   ├─ collect (скрипт)        → collect.json     реестр, OSM, геометрия, Place ID, Commons, пересечения
   ├─ enrich (агенты)         → sources.json     независимые источники, даты, авторы, фото/права
   ├─ adjudicate (агент)      → verdict.json     READY / HOLD / REJECT + пробел + черновик карточки
   ├─ edit (агент/шаблон)     → card.json        карточка + 4 языка + решение по фото
   ├─ validate (скрипт)       → validation.json  схема, полигон, пересечения, сборка, тесты
   └─ integrate (один)        → data/, public/, docs/
```

Каждый кандидат идёт по конвейеру независимо; барьер только на `integrate`. Это и есть «конвейер», но без общей свалки: у каждого этапа свой вход и выход.

### Этап 0. Очередь и владение

`work/queue/index.jsonl` — одна строка на кандидата:

```json
{"n": 15, "reg": 3049, "way": 246769267, "status": "todo",
 "stage": "collect", "lease_until": null, "attempts": 0}
```

Правила:

- статус меняется только через очередь: `todo → collecting → enriching → adjudicating → editing → validating → done / hold / reject`;
- `lease_until` не даёт двум агентам взять одного кандидата;
- ретрай не больше двух; после — `hold` с причиной;
- все артефакты лежат в `work/queue/<n>/`, а не в `docs/`.

### Этап 1. Collect — скрипт, не LLM

Детерминированный сбор, 30–60 секунд на кандидата, батчем по 20:

- реестр: атрибуты + полигон (слой 1 и слой 4, `make_valid`);
- OSM: way/relation, теги, геометрия в порядке `nodes`;
- метрики: площади, IoU, вложенность, смещение центроидов, Hausdorff;
- Place ID из `data/research-next-200-google-place-ids.json`;
- Commons geosearch + поиск по адресу (только кандидаты, без оценки);
- пересечения с уже опубликованными карточками;
- кэш ответов по URL + хэш; повторный запуск не ходит в сеть.

Выход — `collect.json`. Никаких суждений, только факты и ссылки.

### Этап 2. Enrich — агенты, 4–6 минут

Один агент на 2–3 кандидата, только источники:

- 1–3 независимых профильных источника (Scan Tbilisi, TAA, Georgia Travel, NPLG, епархия, официальный перечень);
- даты, авторы, стиль, историческая функция;
- фото: конкретный файл, автор, лицензия, геопривязка, права на архитектуру;
- каждое утверждение — с URL и короткой цитатой/пересказом.

Стоп-правило: **3 поисковых запроса на один неизвестный факт**, дальше `gap` и выход. Это режет 28-минутные выбросы.

Выход — `sources.json`:

```json
{"n": 15, "claims": [{"field": "date", "value": "1863–1864",
  "source": "https://...", "quote": "...", "confidence": "high"}],
 "gaps": ["автор не установлен"], "photos": [...]}
```

### Этап 3. Adjudicate — один агент на батч, 1–2 минуты

Читает `collect.json` + `sources.json`, не ходит в сеть (кроме одного точечного запроса, если совсем не хватает):

- тот ли корпус, тот ли адрес, та ли граница;
- `READY` / `HOLD` / `REJECT`;
- если `READY` — черновик полей карточки;
- если `HOLD` — конкретный пробел и следующий шаг.

Выход — `verdict.json`. Это единственное место, где принимается решение.

### Этап 4. Edit — шаблон + агент, 2–3 минуты на карточку

Никакого research. Только:

- карточка в `data/heritage-extra.json`;
- переводы ru/en/ka/uk (шаблон + проверка);
- фото: WebP, атрибуция, `licenseUrl`, `modifications`;
- `card.json` для валидатора.

Дорогую часть — грузинский и украинский текст — можно делать одним пакетом на 5–10 карточек, а не по одной.

### Этап 5. Validate — скрипт

- JSON-схема и обязательные поля;
- валидность Polygon/MultiPolygon, площадь, самопересечения;
- пересечения с существующими карточками;
- `npm run check`, `npm test`, `npm run build`, `npm run verify`;
- отчёт `validation.json`; при провале карточка не попадает в `data/`.

### Этап 6. Integrate — один писатель

Только здесь меняются `data/`, `public/atlas/`, `docs/`. Один коммит на батч, один регистр, один отчёт. README счётчиков не содержит; статистика генерируется из `buildings.json` скриптом.

## Как развести субпроцессы

| Проблема | Решение |
|---|---|
| Два агента лезут в один файл | Этапы пишут только в `work/queue/<n>/`; `data/` меняет один интегратор |
| Дублирование запросов к реестру/OSM | Collect — один скрипт с кэшем и concurrency 2–3 |
| 429 от OSM | Ограничить параллелизм, backoff, кэш; не запускать 8 агентов на одни и те же way |
| Разные форматы отчётов | JSON-схемы на каждом этапе; свободный текст только в `gap` |
| Агент «уплыл» на 28 минут | Таймбокс этапа + стоп-правило 3 запроса |
| Анализ переворачивается после факта | Adjudicate только после `sources.json` |
| Счётчики расходятся | Убрать числа из README, генерировать статистику |
| Сложно понять, где тормозит | Логировать `started_at`/`finished_at` на каждый этап |

## Что автоматизировать в первую очередь

1. `scripts/queue_collect.py` — реестр, OSM, геометрия, Place ID, Commons, пересечения. Это снимает с агентов самую скучную и повторяемую часть.
2. `scripts/queue_report.py` — регистр и статистика из JSON, без ручного README.
3. `scripts/validate_cards.py` — схема, полигоны, пересечения, сборка.
4. Шаблон карточки и переводов — чтобы Edit не изобретал структуру каждый раз.

Что **не** стоит автоматизировать: вердикт `READY/HOLD` и финальную редактуру грузинского/украинского. Это как раз те места, где нужен человек/сильный агент.

## Ожидаемый эффект

| Этап | Сейчас | После конвейера |
|---|---:|---:|
| Collect (реестр/OSM/геометрия) | 2–4 мин | 0,5–1 мин (скрипт) |
| Enrich (источники) | 5–10 мин | 4–6 мин (таймбокс) |
| Adjudicate | 2–4 мин | 1–2 мин |
| Edit (карточка+переводы) | 4–6 мин | 2–3 мин |
| Validate | 1–2 мин | секунды–1 мин |
| **Итого на кандидата** | **14–26 мин** | **9–13 мин** |

При 4–6 параллельных enriching-агентах это примерно **8 кандидатов за 15–20 минут** вместо 20–28, плюс меньше повторных запросов и меньше «перевернутых» выводов.

Первый фактический прогон (волна 3, 8 кандидатов, 4 агента): collect — 0:18, enrich — 4:33 wall, adjudicate — 0:21, edit одной карточки — ~0:10, validate — ~0:15, отчёт — 1:05; итого **7:14** на волну, 1 ready и 7 hold. Triage-волна оказалась быстрее гипотезы; стоимость READY-тяжёлой волны ещё нужно проверить на 3+ добавлениях. Детали — в [волне 3](research-queue-wave-3.md).

## Реализация в репозитории

Скрипты уже добавлены; они не меняют `data/` и `public/`, поэтому их можно запускать без риска для атласа.

| Скрипт | Что делает | Куда пишет |
|---|---|---|
| `scripts/queue_collect.py` | Реестр, OSM way/relation, геометрия, флаги, Place ID, Commons, пересечения | `work/queue/<n>/collect.json`, `work/queue/index.jsonl` |
| `scripts/queue_report.py` | Сводка по очереди: собрано, IoU, Place ID, ошибки, вердикты | stdout или `--out` |
| `scripts/validate_cards.py` | Схема карточек, переводы, полигоны, фото, пересечения | только отчёт, exit code |

`work/` добавлен в `.gitignore`: это локальный кэш и рабочие артефакты, а не публикуемые данные. HTTP-ответы кэшируются в `work/queue/cache/`; повторный запуск не ходит в сеть без `--refresh`.

### Быстрый старт

```sh
# собрать факты по двум кандидатам (удобно для проверки)
python3 scripts/queue_collect.py --only 28,49 --out work/queue

# собрать всё, что осталось, с паузами между запросами
python3 scripts/queue_collect.py --delay 0.3

# отчёт в файл, не трогая docs/
python3 scripts/queue_report.py --out work/queue/report.md

# проверить исходные карточки перед сборкой
python3 scripts/validate_cards.py
```

Полезные флаги: `--limit`, `--only`, `--refresh`, `--no-commons`. Коллектор по умолчанию идёт последовательно и делает паузу 0,2 с; это специально, чтобы не ловить 429 от OSM. Для чтения уже собранных фактов сеть не нужна. `queue_collect.py` печатает `[N/M]` с ETA, скоростью и отметкой кэша/ошибки; `validate_cards.py` — прогресс по карточкам, зданиям и пересечениям. Общие правила — [long-running-scripts.md](long-running-scripts.md).

### Формат `collect.json`

```json
{"schema": 1,
 "candidate": {"n": 59, "registryId": 3756,
               "osmType": "relation", "osmId": "19630608",
               "osmWay": "1207148736", "osmOverride": "..."},
 "registry": {"attributes": {}, "polygon": {}, "sourceUrls": {}},
 "osm": {"id": "relation/19630608", "type": "relation",
         "tags": {}, "members": [], "polygon": {},
         "sourceUrl": "https://www.openstreetmap.org/relation/19630608"},
 "metrics": {"registryAreaM2": 930.6, "osmAreaM2": 1808.4,
             "iou": 0.372, "osmInsideRegistryPct": 41.1,
             "registryCoveredByOsmPct": 79.9, "centroidDistanceM": 19.6},
 "geometryFlags": ["osm_relation", "underground", "osm_much_larger", "osm_composite_or_plot"],
 "placeId": {}, "commons": [], "atlasOverlaps": [],
 "errors": [], "warnings": [], "fetchedAt": "..."}
```

`geometryFlags` — диагностические, не приговор: `osm_relation`, `underground`, `ruins`, `osm_much_larger`, `osm_much_smaller`, `osm_composite_or_plot`, `official_subset`, `official_point_buffer`, `osm_multi_part`. Они помогают сортировать ручную проверку и не заменяют решение.

### Отношения и overrides

Иногда очередь ссылается на соседний way, а объект описан relation. Исправление хранится явно в `data/osm-candidate-overrides.json`:

```json
{"59": {"type": "relation", "id": 19630608,
        "reason": "Очередь ссылалась на соседний way; баня №5 — relation"}}
```

Коллектор применяет override по номеру кандидата, тянет `relation/<id>`, собирает внешние контуры через `polygonize`, вычитает inner и сохраняет `osm.members`. Пример разбора — [баня №5](research-bath-5-geometry.md). Без override такой объект получил бы чужой way и ложный IoU.

### Primary и вторичные контуры

Карта показывает **надземный след здания**, поэтому primary-геометрия карточки — это он. Официальная граница, relation подземного/составного комплекса, старый way и другие варианты — вторичные: их не выбрасываем, но и не выдаём за footprint.

Вторичные контуры хранятся в `data/geometry-variants.json`:

```json
{"schema": 1,
 "objects": {
   "osm-19630608": {
     "primary": null,
     "primaryRole": "above_ground_footprint",
     "missing": ["above_ground_footprint"],
     "variants": [
       {"id": "official-3756", "role": "heritage_boundary", "areaM2": 930.6, "geometry": {}},
       {"id": "osm-relation-19630608", "role": "complex_underground", "areaM2": 1808.4, "geometry": {}},
       {"id": "osm-way-1207148736", "role": "neighbor_wrong_candidate", "areaM2": 266.6, "geometry": {}}
     ]}}}
```

Правила:

- `primary` — надземный контур, если он есть. Если его нет, допускается fallback `geometryRole=heritage_boundary`: карта рисует охраняемое ядро пунктиром и предупреждает, что это не footprint. Relation подземного комплекса на роль primary не подходит.
- `variants[].role` фиксирует смысл: `heritage_boundary`, `complex_underground`, `neighbor_wrong_candidate`, `historic_plan`, `visible_domes`.
- Когда появится обмер куполов, он становится `primary`, а старые варианты остаются в файле.
- В данных это поля `geometry` (что рисуется), `geometryRole` (`above_ground` / `heritage_boundary` / …) и `geometryVariants`. `MapView` меняет стиль по роли, инспектор показывает предупреждение.
- Представление можно перестроить по типу геометрии: карта берёт `primary`, а инспектор/исследование — нужный variant.

`queue_report.py` читает `index.jsonl`; если появится `work/queue/<n>/verdict.json`, колонка «Вердикт» подхватит его автоматически.

### Что ещё не автоматизировано

- `enrich` (независимые источники), `adjudicate` (READY/HOLD/REJECT) и `edit` (переводы и карточка) пока остаются агентскими этапами. Для них нужен формат `sources.json` / `verdict.json` / `card.json`, описанный выше.
- `validate_cards.py` проверяет источник, но не заменяет `npm run check` и `npm test`: после `build-data.py` всё равно нужны штатные проверки.
- Автоматического переноса `verdict.json` в `data/` нет намеренно: это должен делать один интегратор после просмотра.

## Что уже сделано по этой заметке

- Добавлены `queue_collect.py`, `queue_report.py`, `validate_cards.py`; `work/` исключён из git.
- Из README убраны счётчики зданий/фото/дат: теперь там описание продукта, а не моментальный снимок.
- `AGENTS.md` больше не хранит числа, а отправляет за актуальными значениями в `public/atlas/buildings.json` и манифест.
- `docs/status.md` — текущий снимок с датой; его числа не «живой счётчик» и обновляются вместе со статусом.

Первый практический шаг при возвращении к работе: прогнать `queue_collect.py` по всем 126 оставшимся, не запуская LLM. Это даст полную таблицу «что уже известно» и покажет, сколько кандидатов отсеивается по геометрии/адресу до исследования.
